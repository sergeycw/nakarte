# BRouter в браузере: отчёт по эксперименту с CheerpJ

Дата: 2026-10-06. Ветка `exp/brouter-wasm`, worktree `../nakarte-wasm`.

## Коротко

BRouter без единой правки алгоритма работает в браузере через CheerpJ 4.3 и даёт **тот же маршрут, что сервер**: на всех 6 эталонах совпали и длина до метра, и число точек. Предложенный порог пройден с запасом:

| Критерий | Порог | Результат |
|---|---|---|
| ≈10 км, тёплый старт | < 2 с | 0.30–0.55 с |
| Рантайм + jar по сети | < 30 МБ | ≈11 МБ на холодном старте, ≈0.3 МБ на тёплом |
| Длина маршрута | ±1% | 0% на 6/6 |

Узкие места не в скорости расчёта. Это холодный старт (~5 с до первого маршрута), память вкладки (~0.6–0.8 ГБ RSS) и условия лицензии: бесплатно, только если рантайм грузится с CDN Leaning Technologies.

Рекомендация: подключать CheerpJ к nakarte за флагом (шаг 4). Для апстрима параллельно проверить BeeRouter (форк BRouter на Kotlin Multiplatform) с таргетом Kotlin/Wasm, а если не выйдет - TeaVM. Valhalla не рассматривать.

## Что сделано

- `baseline/`: эталон с серверного BRouter (`localhost:17777`), 3 маршрута × 2 профиля, GeoJSON и `summary.json`. Скрипт `run.mjs`.
- `cheerpj/java/WasmRouter.java`: обёртка, которая повторяет путь `RouteServer` без сокетов: `RoutingParamCollector` → `RoutingEngine.doRun` → `FormatJson`. Принимает ту же query-строку, что HTTP API, поэтому `profile:<var>` работает: `path_preference=20` даёт 3830 м, как на сервере.
- `cheerpj/index.html`: стенд вне сборки nakarte. Параметры: `fs=str|app` (как тайлы попадают в Java), `rt=proxy` (рантайм через локальный прокси), `repeat`, `only`.
- `cheerpj/patch/`: однострочный патч `NodesCache` для режима `fs=app` (подробности ниже).
- `serve.mjs`: статика с Range, счётчик отданных байт (`/__stats`), задержка `DELAY_MS`, прокси рантайма `/cjrt/`, заголовки COOP/COEP по `COI=1`.
- `TEAVM-AUDIT.md`: статический аудит пути через TeaVM.

Маршруты: `routes.json`. Профили: `hiking-mountain` и `trekking` (велосипедный). BRouter: образ `nightly`, ревизия `29898106`, 1.7.11-beta. jar собран под Java 11 (class version 55), CheerpJ запускается с `version: 11`.

### Старт

| Этап | Холодный (пустой кеш) | Тёплый (HTTP-кеш) |
|---|---|---|
| `cheerpjInit` | 0.6–1.4 с | 0.03–0.05 с |
| `cheerpjRunLibrary` (загрузка JDK и jar) | 2.5–3.8 с | 0.7 с через прокси с кешем, 1.5–2.5 с с CDN |
| первый маршрут | 1.0–1.9 с | 0.85 с |
| итого до первого маршрута | ≈5–6 с | ≈1.6–4 с |

На тёплом старте с CDN `cheerpjRunLibrary` заметно медленнее, чем через прокси. Скорее всего, часть Range-кусков JDK CDN кешировать не даёт. Проверить не удалось: эти запросы идут из cross-origin iframe, и расширение их не видит.

### Тайлы

| Режим | Как | Скачано |
|---|---|---|
| `fs=str` | два тайла целиком в `/str/` через `cheerpOSAddStringFile` | 48.4 МБ, 0.2–0.4 с на localhost |
| `fs=app` | CheerpJ читает тайл кусками по 128 КБ через Range | short: 1.9 МБ, все 6 маршрутов × 3 прогона: 6.1 МБ |

Скорость расчёта в обоих режимах одинаковая. Куски кешируются внутри сессии: повторы того же района в сеть не ходят. Гипотеза про Range подтвердилась по коду и на практике. Подробности формата есть в `TEAVM-AUDIT.md`, §1: заголовок 200 байт, индекс 1°-подтайла 4 КБ, затем ячейки по 1/32°, медиана ячейки 0.6–0.8 КБ. CheerpJ выбирает с запасом: кусок 128 КБ против ~1 КБ полезных данных, но в сумме это всё равно единицы мегабайт.

### Память

| Где | Как | Пик |
|---|---|---|
| headless Chrome 154, `fs=str` | RSS процесса-рендерера | 562 МБ |
| headless Chrome 154, `fs=app` | RSS процесса-рендерера | 589 МБ |
| рабочий Chrome 153, `fs=app` | прирост RSS рендерера вкладки (шумно, открыты другие вкладки) | ≈720 МБ |
| рабочий Chrome 153 | `performance.measureUserAgentSpecificMemory()` под COOP/COEP | 82 МБ |

Последняя цифра учитывает только JS-кучу. Память wasm и сгенерированный JIT-код, судя по разнице с RSS, в неё не входят, это вывод из цифр, а не из документации. Ориентир для отчёта: **0.6–0.8 ГБ RSS на вкладку**. Для десктопа терпимо, для телефона риск.

### Отзывчивость UI

Замер через `MessageChannel`-пинг во время расчёта:

- 10 км: максимальная пауза главного потока 69 мс;
- 40 км: три паузы, в сумме 1.0 с из 1.3 с, самая длинная 555 мс.

На отрезках, которые прокладывает редактор (обычно до нескольких км), UI не замерзает. Длинный маршрут одним куском подвешивает страницу на полсекунды.

## Что сработало и что нет

Сработало:

- jar из образа без пересборки, обёртка на 40 строк, Java 11 в CheerpJ.
- Совпадение с сервером 1:1, включая `profile:` переопределения.
- Чтение тайлов через HTTP Range силами самого CheerpJ (`/app/`).
- Прокси рантайма вместе с COOP/COEP: CheerpJ под cross-origin isolation не ломается.

Подвохи, найденные по ходу:

- `/str/` плоская: путь `/str/profiles/lookups.dat` даёт `FileNotFoundException`, `/str/lookups.dat` работает.
- В `/app/` нет каталогов. `stat` делается запросом `Range: bytes=0-0`, длина берётся из `Content-Range`, а `isDirectory()` всегда `false`. Даже `/app/cheerpj`, который сервер отдаёт как `index.html`, считается файлом. `NodesCache` проверяет `segmentDir.isDirectory()` и падает с ошибкой `segment directory /app/segments4 does not exist`. Лечится патчем в одну строку (`cheerpj/patch`): для путей `/app/` проверка пропускается. В документации CheerpJ это не описано.
- Без патча, точнее с проверкой `isDirectory()` до префикса, каждый расчёт делал ~6 пустых запросов `GET /segments4`: `NodesCache` создаётся несколько раз за маршрут, а отрицательный ответ CheerpJ не кеширует. На задержке 40 мс это +300 мс к каждому маршруту. Сейчас таких запросов 0.
- Остаётся 1 запрос `storageconfig.txt` на маршрут (`StorageConfigHelper`), он отвечает 404. Его закрывает пустой файл с кешированием на раздаче.
- На страницу допускается один library-поток: повторный `cheerpjRunLibrary` бросает `Only one library thread supported`. Для nakarte это значит один экземпляр на страницу и очередь запросов. Редактор шлёт `routeBetween` параллельно, CheerpJ выполнит их по одному.
- Рантайм грузит JDK из cross-origin iframe `c.html`, поэтому сеть и память iframe не видны ни сессии CDP страницы, ни расширению. Для честного учёта понадобился прокси.
- Для раздачи тайлов с другого origin нужны CORS и `Access-Control-Expose-Headers: Content-Range`: CheerpJ берёт размер файла из этого заголовка.

Не проверено:

- Firefox и Safari, мобильные браузеры.
- Реальная сеть до чужого CDN тайлов: задержка эмулировалась на localhost.
- Рантайм в Web Worker. Я не нашёл подтверждения, что CheerpJ library mode умеет работать в воркере, поэтому не утверждаю ни того, ни другого.

## Лицензия CheerpJ

По [cheerpj.com/docs/licensing](https://cheerpj.com/docs/licensing): Community License бесплатна для частных лиц и FOSS при условии указать авторство. Бесплатное использование ограничено рантаймом с домена `cjrtnc.leaningtech.com`, для self-hosting нужна коммерческая лицензия. Для локального форка это не мешает. Для апстрима nakarte.me получит зависимость от чужого CDN. Прокси `/cjrt/` в стенде - только инструмент замера, в продукт его нести нельзя.

## Путь через TeaVM

Полный аудит лежит в `TEAVM-AUDIT.md`, его делал отдельный агент по исходникам BRouter `29898106` и TeaVM `master` (0.16.0). Ключевые места я сверил с кодом сам.

- Файлы. В classlib TeaVM есть `File`, `RandomAccessFile`, `FileInputStream`, `FileReader`. Они работают через `VirtualFileSystemProvider`, по умолчанию это ФС в памяти. Код `PhysicalFile` и `OsmFile` компилируется как есть. Чтобы подложить HTTP Range, нужно подменить ФС через `setInstance()`, а это внутренний, недокументированный API.
- Синхронный I/O - главная проблема. Чтение тайла происходит внутри цикла A* (`RoutingEngine.java:2198`, `:2218` → `NodesCache` → `OsmFile.readFully`). Варианты: тайл целиком в памяти (PoC), Web Worker с sync XHR + Range или OPFS `FileSystemSyncAccessHandle`. Третий вариант - `@Async` в TeaVM, но он превращает весь A* в корутину.
- Рефлексия и что ломает сборку:
  - `StackSampler` (`Thread.getAllStackTraces`, `Locale.Builder`) достижим из конструктора `RoutingEngine.java:128`, его нужна заглушка;
  - `Class.forName` в `RoutingContext.java:91` нужно заменить на `switch`, затронут только `car-vario`.

  Proxy, ServiceLoader, сериализации, `java.nio` и `zip` на пути маршрутизации нет.
- Потоки. `doRun` синхронный, ExecutorService, Timer и wait/notify отсутствуют, `synchronized` только на `openSet` и `ProfileCache`.
- Риски:
  - скорость A* в Wasm GC и JS никто не мерил, в JS-бэкенде `long` через BigInt медленный;
  - возможны расхождения `float` с сервером в JS-бэкенде;
  - Wasm GC требует Chrome 137+, Firefox 131+, Safari 18.4+.
- Объём: обязательные правки BRouter - 2 класса, ~25 строк. Нового кода 400–600 строк. PoC за 1–2 дня, рабочая версия за 5–9 дней.

Плюсы относительно CheerpJ: нет чужого CDN и лицензионных ограничений, бандл, вероятно, меньше, а память и старт должны быть заметно ниже - но это предположение до сборки, цифр нет.

## Valhalla и остальные варианты

Обзор со ссылками лежит в `ALTERNATIVES.md`, руками я эти варианты не запускал. Самая важная находка там - BeeRouter: форк BRouter на Kotlin Multiplatform под MPL-2.0. Он читает те же `.brf`, `.rd5` и `lookups.dat`, на Maven Central лежит 0.0.6 от 2026-09-28, артефакты пока только `jvm` и `linuxx64`. Это проверено по README на Codeberg и по `maven-metadata.xml`. Сборку под Kotlin/Wasm никто не публиковал.

Valhalla в Wasm (`tobilg/valhalla-wasm`) существует и работает: тайлы читаются по Range, wasm весит 9.9 МБ. Причин переходить на неё нет: BRouter уже работает в браузере, совпадает с сервером, его профили и `profile:` переопределения в nakarte уже используются. Valhalla - другой движок с другими тайлами и профилями. Это ещё и отдельная сборка и раздача данных, и переписывание активностей. Смысл возвращаться к ней появится, только если и CheerpJ, и TeaVM упрутся в память на мобильных.

## Рекомендация

1. **Шаг 4 делать на CheerpJ.** Скорость, точность и объём скачивания с запасом проходят порог. Работа: флаг `config.routingEngine`, ленивая инициализация при первом включении роутинга (а лучше заранее, в фоне), очередь запросов в одном library-потоке, патч `NodesCache`, раздача тайлов с Range и CORS, пустой `storageconfig.txt`. Контракт `fetchRoute` при этом не меняется.
2. **План Б для апстрима** нужен, если автор nakarte не примет зависимость от `cjrtnc.leaningtech.com` или 0.7 ГБ на вкладку окажется слишком много:
   - первым - спайк BeeRouter с таргетом `wasmJs`: прогнать те же 6 эталонов;
   - вторым - PoC на TeaVM на 1–2 дня, тайл в памяти.
3. Valhalla - нет.

## Предлагаемая правка порога

Порог «10 км < 2 с» слишком мягкий: CheerpJ проходит его в 4–6 раз. Что реально влияет на ощущения в редакторе:

- отрезок до 3 км на тёплом движке быстрее 300 мс (сейчас 140–250);
- от включения роутинга до первого маршрута на тёплом кеше меньше 3 с, на холодном меньше 8 с (сейчас ≈1.6–3.5 и ≈5–6);
- пауза главного потока на отрезке до 10 км меньше 100 мс (сейчас 69);
- память вкладки на десктопе меньше 1 ГБ RSS (сейчас 0.6–0.8).

## Как повторить

```sh
cd experiments/wasm
node baseline/run.mjs                 # эталон, нужен контейнер nakarte-brouter
cheerpj/build.sh                      # jar и профили из контейнера, обёртка, патч
node serve.mjs                        # стенд на 127.0.0.1:8767; DELAY_MS=40, COI=1 по желанию
# http://127.0.0.1:8767/cheerpj/?fs=app&repeat=3
# http://127.0.0.1:8767/cheerpj/?fs=app&rt=proxy&repeat=3   (байты рантайма в /__stats)
```

`cheerpj/bench.mjs` - headless-прогон через Playwright с замером RSS (`PLAYWRIGHT_CORE=<путь к playwright-core>`). Основные цифры отчёта сняты в рабочем Chrome.
