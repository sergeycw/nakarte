# Design

## Context

Мотивация — в `proposal.md`. Клиент: `src/lib/leaflet.layer.westraPasses/` (4 файла от `westraDataBaseUrl`) и `src/lib/leaflet.layer.geocaching-su/` (один файл `geocachingSuUrl`). Файлы автора на 2026-10-07: `westra_passes2.json` ≈ 7.4 МБ без сжатия, объект `{passes, regions}`; `geocaching_su2.json` — массив из 31 084 элементов `[name, id, lat, lng]`; оба обновлены в тот же день, отдаются с `Access-Control-Allow-Origin: *`. Как автор получает данные, публично не описано. `robots.txt` westra.ru запрещает, среди прочего, `/passes/Passes/0`, `/passes/Reports/0`, `/passes/Maps/0`.

## Goals / Non-Goals

**Goals:**
- Те же файлы и схема, что у автора, без правок клиента.
- Ежедневное обновление без ручной работы.

**Non-Goals:**
- Свой формат данных или новые поля в слоях.
- Отчёты и фото перевалов, кроме счётчиков, которые уже есть в схеме.

## Decisions

### Сначала источник, потом код

Первая задача — найти, откуда брать данные: официальный экспорт или API westra.ru (KML, выгрузка каталога) и geocaching.su, условия использования, ограничения `robots.txt`. Предпочтение — массовая выгрузка одним-несколькими запросами, а не обход тысяч страниц. Если подходящего пути нет или условия запрещают сбор, change останавливается и вопрос уходит владельцу.

### Cron Trigger → R2, раздача тем же Worker

Один Worker `workers/scrapers/`: обработчик `scheduled` раз в сутки собирает данные и пишет файлы в R2 только после проверки схемы и непустоты; обработчик `fetch` отдаёт файлы по `/westraPasses/<файл>` и `/geocachingSu/<файл>`. Лимит CPU у cron с интервалом от часа — 15 мин; если сборке этого мало, она режется на этапы с промежуточным состоянием в R2. Альтернатива — cron на GitHub Actions с загрузкой в R2: проще отлаживать, но держит секреты R2 в CI; выбирается, если сбор упрётся в лимиты Workers, и фиксируется здесь.

### Схема как контракт

Схемы обоих файлов снимаются с файлов автора и лежат фикстурами; сборщик проверяет результат против них до записи. Тесты разбора идут на сохранённых ответах источников, без сети.

## Risks / Trade-offs

- [Условия westra.ru или geocaching.su запрещают сбор] → проверка первой задачей, при запрете — стоп и вопрос владельцу.
- [Источник меняет вёрстку или формат] → проверка схемы не даёт записать сломанные данные; сбой виден в логах, старые файлы остаются.
- [Нагрузка на источники] → раз в сутки, паузы, свой `User-Agent`.

## Migration Plan

Сбор и проверка файлов → раздача → переключение ключей в `config-target/clone.js`. Откат — вернуть URL автора.
