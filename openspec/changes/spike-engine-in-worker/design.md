# Design

## Context

Зачем — [proposal](proposal.md). Ограничения движка, которые от UI не зависят, — спека [browser-routing-engine](../../specs/browser-routing-engine/spec.md) и `AGENTS.md`, [«Движок в браузере (CheerpJ)»](../../../AGENTS.md#движок-в-браузере-cheerpj); решения про движок в новом приложении — [ресёрч, п. 4](../../research/new-ui.md#cheerpj-в-новом-приложении); каркас `web/` — архив [add-web-skeleton](../archive/2026-10-08-add-web-skeleton/design.md). Справочник — движок старого клиента [browser-engine.js](../../../src/lib/brouter/browser-engine.js): загрузчик с CDN, `cheerpjInit({version: 11})`, `cheerpjRunLibrary` с `brouter-patch.jar:brouter.jar:wasm-router.jar`, очередь промисов, всё на главном потоке.

Первоисточники CheerpJ, сверено 2026-10-08: [changelog](https://cheerpj.com/docs/changelog.html) — «Support for Web Workers (just use `importScripts`)» в 3.0rc2 (2023-11-29), последняя версия 4.3 (2026-04-21); [Migration from CheerpJ 2](https://cheerpj.com/docs/migrating-from-cheerpj2.html) — `CheerpJWorker` убран, в воркере `importScripts` и дальше «as usual»; [cheerpjInit](https://cheerpj.com/docs/reference/cheerpjInit.html) — «must be called once in the page», про воркеры ничего. Vite: [Features → Web Workers](https://vite.dev/guide/features.html#web-workers) — воркер находится только по `new Worker(new URL(..., import.meta.url))`, в dev ESM в воркере опирается на поддержку браузера; [worker.format](https://vite.dev/config/worker-options.html) по умолчанию `'iife'`.

## Goals / Non-Goals

**Goals:**
- Ответы спайка (ниже, «Проверки») и модуль движка, который редактор маршрута (change 5) вызывает без переделки.
- Локальный стенд нового приложения с настоящим движком: dev-сервер отдаёт файлы движка так же, как Pages Functions на проде.

**Non-Goals:**
- UI прокладки, активности, состояние «движок загружается» на кнопке — change 5 (`add-web-route-editor`); здесь только API, на котором оно строится.
- Перевод запроса BRouter и разбор GeoJSON в точки отрезка (`buildRouteParams`, `buildSegmentNodes` старого клиента) — change 5: движок принимает строку запроса и отдаёт строку GeoJSON.
- Старый клиент: остаётся на главном потоке.

## Проверки

Стенд — `web/engine-bench.html` (параметры: `backend=worker|main-thread`, `q=` запрос BRouter, `runs=`), dev-сервер `web/` с файлами движка из `experiments/wasm/cheerpj/` и тайлом `E40_N40` из `brouter/segments4/`. Блокировку меряет MessageChannel-пинг: каждая задача шлёт себе следующую, пауза между пингами — время, которое главный поток был занят. Long task — пауза больше 50 мс. 2026-10-08, CheerpJ 4.3, Chromium из Playwright 1.64 (headless, чистый профиль — холодный кеш CDN) и браузерная панель Claude (тёплый кеш).

### CheerpJ в Web Worker

- **Работает в классическом воркере.** `importScripts('https://cjrtnc.leaningtech.com/4.3/loader.js')`, `cheerpjInit({version: 11, status: 'none'})`, `cheerpjRunLibrary(classpath)` и `WasmRouter.route(...)` в воркере дают тот же маршрут, что на главном потоке (2762 м, 141 точка на коротком; 29 728 м, 1045 точек на длинном).
- **Module-воркер не годится.** В module-воркере нет `importScripts`, а загрузчик объявляет `cheerpjInit` глобальной функцией (`function cheerpjInit(...)` в `loader.js`) и ищет свой адрес по стеку исключения, так что `import()` или `eval` текста его не заменят.
- **`/app/` — корень origin, и из воркера, и со страницы `/next/`.** `WasmRouter.probe` из воркера видит `/app/brouter-wasm/segments4/E40_N40.rd5` (30 743 932 байт) и `/app/brouter-wasm/lib/brouter.jar` (2 344 875) — запросы уходят на `/brouter-wasm/...`, а не на `/next/brouter-wasm/...`. Range, `206` и `Content-Range` нужны так же, как на странице.
- **Один library-поток на глобальную область, а не на страницу.** Второй `cheerpjRunLibrary` в том же воркере — `Only one library thread supported`, второй `cheerpjInit` — `CheerpJ: Already initialized`. Два воркера на одной странице и экземпляр на главном потоке работают одновременно и независимо. Значит, перезапуск после сбоя чистый, если создать новый воркер; на главном потоке повторный `cheerpjInit` бросает.
- **Vite в dev отдаёт воркер почти без сборки.** В классическом воркере любой `import` — `Cannot use import statement outside a module`; даже после `import type` Vite оставляет `export {}` — `Unexpected token 'export'`. В production-сборке воркер — IIFE без импортов (проверено `vite build` + `vite preview` со стендом).

### Холодный старт и блокировка главного потока

Три прогона на чистом профиле; разброс холодного старта — CDN. Длинный маршрут — Тбилиси → Мцхета, `44.776,41.687|44.718,41.842`, `hiking-mountain`, 29.7 км. Холодный старт — от вызова до готового `WasmRouter`, с загрузкой рантайма с CDN.

| | холодный старт | 1-й маршрут | следующие | макс. пауза главного потока | long tasks за маршрут |
|---|---|---|---|---|---|
| воркер | 4.2–6.1 с (2.8–3.8 с на эмуляции Pixel 7) | 2.2–2.9 с | 0.79–0.96 с | ≤ 10 мс на старте, ≤ 5 мс на маршруте | 0 |
| главный поток | 5.4–6.2 с | 2.0–2.3 с | 0.77–0.95 с | 46–51 мс на старте, 281–341 мс на маршруте | 0.66–0.84 с |
| воркер, production-сборка | 4.9 с | 1.4 с (короткий) | 0.15 с | ≤ 10 мс | 0 |

На главном потоке за тёплый маршрут проходит 9 пингов из ≈ 450 тысяч у воркера: страница стоит почти весь расчёт. В воркере расчёт идёт с той же скоростью, а страница свободна. С тёплым кешем CDN старт в воркере — 1.4 с.

### Память вкладки

Playwright, профиль `Pixel 7` (412×839, DPR 2.625), dev-сервер, реальные тайлы OSM; сумма по дереву процессов Chromium, два прогона. Две метрики: RSS (как в архиве add-web-skeleton) и `phys_footprint` macOS (`footprint`). RSS на macOS не учитывает сжатую память и падает, пока память ещё занята, поэтому для выводов — `phys_footprint`.

| момент | RSS, МБ | phys_footprint, МБ |
|---|---|---|
| пустая вкладка | 239 | 44 |
| карта MapLibre | 458–462 | 241–242 |
| карта + движок в воркере, после 3 длинных маршрутов | 561–624 | 524–541 |
| через 30 с простоя | 327–347 | 434–454 |
| без карты, только движок (десктоп): воркер / главный поток | 729–791 / 592–1054 | 469–531 / 530–582 |

Движок добавляет к карте ≈ 0.3 ГБ, вкладка с картой и движком — ≈ 0.55 ГБ на пике против оценки 1–1.1 ГБ из архива add-web-skeleton (там 0.6–0.8 ГБ движка — оценка старого стенда по RSS). Резерв (`pixelRatio` карты, кеш тайлов) сейчас не нужен. Ограничения: headless Chromium на macOS, WebGL через SwiftShader, эмуляция не ограничивает память как телефон. На живом телефоне не проверено — устройства и симулятора в сессии нет; проверить на проде по `/next/engine-bench.html` при первой возможности.

## Decisions

Решений, которых нет в ресёрче, архивах и задаче change, три — помечены **[владелец]**; владелец подтвердил их 2026-10-08.

### Классический воркер, обвязка CheerpJ в нём повторена

`engine.worker.ts` — классический воркер (`new Worker(new URL('./engine.worker.ts', import.meta.url))` без `type: 'module'`) без единого импорта: так он работает и в dev, и в сборке («Проверки»). Типы сообщений — глобальные (`protocol.d.ts`, `declare namespace EngineProtocol`), а обвязка CheerpJ (`importScripts`, `cheerpjInit`, `cheerpjRunLibrary`, текст исключения Java) повторяет `loadRouter` из `cheerpj-router.ts`, которым пользуется запасной путь. Отвергнуто: module-воркер (нет `importScripts`); воркер простым JS в `public/` (без типов и без хеша в имени — кеш браузера держит старую версию); свой плагин Vite, собирающий воркер в dev (сложнее, чем 20 повторённых строк). Оба места ссылаются друг на друга комментарием.

### `engine.ts`: синглтон, очередь, промисы

- `createEngine(backends)` — движок над списком бэкендов (`EngineBackend`: `start`, `route`, `dispose`); `getEngine()` создаёт синглтон лениво при первом вызове, импорт модуля ничего не грузит. `startEngine()` — прогрев (редактор вызывает его при выборе активности, не в эффекте), `routeInEngine(query, signal)` — маршрут в очереди.
- Компоненты получают только промисы; для состояния кнопки активности — `status()` (`idle | loading | ready | failed`) и `subscribe()`, под `useSyncExternalStore`.
- Очередь — хвост промисов, как в старом клиенте, но на стороне страницы: в воркер уходит по одному запросу, поэтому отмена из очереди не требует протокола отмены.
- Ошибки: `EngineStartError` — движок не запустился нигде (для UI — «роутер недоступен»); остальные — `Error` с текстом исключения Java (`no route found`, `datafile E40_N40.rd5 not found` и т. п.); отмена — `signal.reason` (`AbortError`).
- Адрес загрузчика CheerpJ — `routingEngineRuntimeUrl` в `web/src/config.ts`: одно место адресов сервисов (AGENTS.md, «Новое приложение»).

### Запасной путь на главном потоке

Порядок бэкендов — `[воркер, главный поток]`. Если воркер не поднялся (событие `error`, `start-failed`), он завершается, и в той же попытке запускается CheerpJ на главном потоке. Если не поднялось ничего — `EngineStartError`, следующий запрос снова начинает с воркера (спека, «Сбой запуска»). Повторный запуск на главном потоке пропускает загрузку скрипта и `cheerpjInit`, если они уже прошли: второй `cheerpjInit` бросает. Где воркер падает, а главный поток работает: CSP `worker-src`, сбой CheerpJ в воркере в другом браузере (Safari не проверен). Цена: при недоступном CDN две быстрые неудачи вместо одной.

### Отмена: из очереди — да, начатый расчёт не прерывается **[владелец]**

`routeInEngine(query, signal)`: отменённый в очереди запрос сразу отклоняется и в движок не уходит; отменённый во время расчёта — отклоняется сразу, но движок дочитает его, и следующий запрос начнётся после. Альтернатива — `worker.terminate()` и новый воркер — прерывает расчёт мгновенно, но стоит холодного старта 1.4–4 с против оставшихся 0.2–3 с расчёта, и на главном потоке так не сделать. Редактору (change 5) этого хватает: устаревшие ответы он и так отбрасывает ([route-editing](../../specs/route-editing/spec.md)).

### Один воркер на страницу **[владелец]**

Хотя CheerpJ позволяет по экземпляру на воркер, движок держит один: каждый экземпляр — ≈ 0.3–0.5 ГБ, а очередь из быстрых кликов и так проходит за секунды. Параллельный расчёт отрезков несколькими воркерами — пункт в backlog, «Варианты движка в браузере», с ценой по памяти.

### Стенд `engine-bench.html` в сборке **[владелец]**

Приложение до change 5 движок не вызывает, и без страницы со стендом на проде нечем проверить воркер, `/app/` со страницы `/next/` и Range Pages Functions. `engine-bench.html` — второй вход сборки Vite (`build.rollupOptions.input`), выкатывается по `/next/engine-bench.html`, ссылок на него нет; рантайм грузится только при его открытии. Альтернатива — только в dev, а проверку на проде отложить до change 5. Стенд остаётся для будущих замеров (живой телефон, Safari) и удаляется, когда редактор даст такие же цифры из приложения.

### Файлы движка в dev-сервере и `vite preview`

Плагин `web/vite/engine-files.ts` вешает middleware до внутренних Vite (пути вне `base: '/next/'`): `/brouter-wasm/lib/` и `/brouter-wasm/profiles/` — из `experiments/wasm/cheerpj/` после `build.sh`, `/brouter-wasm/segments4/` — из `brouter/segments4/` (режим без `clone`, `routingTilesPath` — `/brouter-wasm/segments4/`), пустой `storageconfig.txt`. Range — тот же разбор, что в [functions/brouter-wasm](../../../functions/brouter-wasm/[[path]].js): `206` с `Content-Range`, суффикс, `416`. `/tiles/` (режим `clone`, `npm run dev:clone`) — `server.proxy` на `nakarte-tiles-worker` (8788), как у старого dev-сервера ([webpack.config.js](../../../webpack/webpack.config.js), `devServer`). Почему не статика Vite: каталоги вне `root`, и без `206` CheerpJ не видит размер файла. Тот же middleware стоит и в `vite preview`, чтобы стенд работал на production-сборке; e2e эти пути не трогает.

### Тесты

- **Unit (Node):** `engine.test.ts` с поддельными бэкендами — порядок очереди, ошибка одного запроса не мешает следующим, отмена в очереди и во время расчёта, запасной путь, повторный запуск после сбоя, один запуск на много вызовов, импорт без побочных эффектов; `engine-files.test.ts` — Range (`206`, суффикс, `416`, без заголовка — `200`), выход за каталог, пустой `storageconfig.txt` через настоящий HTTP-сервер на временном каталоге.
- **Browser mode:** `backends.browser.test.ts` — протокол `workerBackend` против поддельного воркера (тот же протокол, без CheerpJ): старт, ответ, ошибка маршрута, падение воркера отклоняет ожидающие запросы. Фабрика воркера — параметр `workerBackend` со значением по умолчанию.
- **e2e:** «Прокладка выключена» — открытие `/next/` не запрашивает ни `cjrtnc.leaningtech.com`, ни `/brouter-wasm/`, ни `/tiles/`.
- Настоящий движок (CDN) — стенд вручную и на проде, сценарии «Маршрут не подвешивает страницу» и «Страница на /next/».

## Risks / Trade-offs

- [Обвязка CheerpJ в двух местах] → обе короткие и ссылаются друг на друга; разъедутся — сломается запасной путь, а он редкий. Проверка вручную стендом с `backend=main-thread`.
- [Safari и iOS не проверены] → стенд на проде открывается с телефона; если воркер там не взлетит, сработает запасной путь.
- [CheerpJ в воркере держит отдельную копию JDK-кеша от главного потока] → только если сработали оба бэкенда; один движок на страницу этого не допускает.
- [Воркер умер молча (браузер выгрузил его по памяти) — событие `error` не приходит, запрос в нём повиснет] → не наблюдалось; если всплывёт в change 5, таймаут запроса в `engine.ts` больше `maxRunningTime` BRouter (60 с в `WasmRouter`) с перезапуском воркера.
- [Стенд на проде открыт всем] → рантайм грузит только тот, кто открыл; Pages Functions за счётчиком `GUARD` ([worker-limits](../../specs/worker-limits/spec.md)).

## Migration Plan

1. PR в `master`, `check web` зелёный.
2. Merge → `deploy pages` выкатывает `/next/` и `/next/engine-bench.html`.
3. На проде: стенд в воркере и на главном потоке — `/app/` со страницы `/next/`, Range через Pages Functions, тайлы `/tiles/`, замеры; итог — в этот design, архив — вторым PR.
4. Откат — revert и push.
