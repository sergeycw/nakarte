# Design

## Context

Деплой — четыре job'а в `deploy-pages.yml`, у каждого `env: CLOUDFLARE_API_TOKEN` на уровне job'а. GitHub передаёт секрет в окружение каждого шага job'а; код любого шага (скрипт `postinstall` пакета, `build.rs` крейта, действие) может прочитать и отправить его наружу. Секрет, заданный в `env` шага, в окружении других шагов отсутствует.

## Goals / Non-Goals

**Goals:** токен видят только шаги `wrangler` и только закреплённой версии; сторонний код, исполняемый до них, его не получает.

**Non-Goals:**
- Защита от подмены самого `wrangler` в npm: закрепление версии защищает от новой вредной версии, но не от подмены опубликованной (npm это запрещает).
- Подмена кода, который потом исполняется в шаге с токеном: зависимость при установке может переписать файлы в `node_modules`, а `npx` берёт `wrangler` оттуда, если версия совпадает. Полную изоляцию дал бы отдельный job публикации, получающий только артефакт сборки, — P3.
- Environment `production` для секретов — сначала шаг владельца (backlog).

## Decisions

- **`env` на шаге, а не на job'е.** Самая дешёвая правка с наибольшим эффектом: `yarnpkg`, `npm ci`, `cargo` и `rust-cache` больше не видят токен. `CLOUDFLARE_ACCOUNT_ID` уходит туда же — не секрет, но смысла держать его шире нет.
- **SHA с тегом в комментарии** (`uses: actions/checkout@3d3c… # v7.0.1`). GitHub называет SHA единственным неизменяемым способом ([secure use](https://docs.github.com/en/actions/reference/security/secure-use)). SHA взяты по тегам последних релизов 2026-10-08, совпадают с текущими мажорными тегами. Политику репозитория «require SHA pinning» не включаем: она уронит апстримный `main.yml`.
- **`WRANGLER: wrangler@4.148.0` на уровне workflow** — одно место на workflow, скрипт синхронизации читает ту же переменную (по умолчанию `wrangler@4` для локального запуска). Это версия, которой CI деплоит сейчас.
- **`CLOUDFLARE_TILES_TOKEN || CLOUDFLARE_API_TOKEN`.** Узкий токен синхронизации можно завести без одновременной правки workflow, а широкий токен потом сузить до деплоя. Работает ли `wrangler r2 object put` с токеном на один бакет, документация не говорит — проверка владельца ручным запуском.

## Risks / Trade-offs

- [Сборка wasm в шаге `wrangler deploy` у `nakarte-elevation`] → `wrangler` всегда запускает `[build]` (`worker-build`), то есть `cargo` в шаге с токеном. Крейты к этому моменту уже собраны `npm test`, и `cargo` не перезапускает их `build.rs`; полная изоляция — тот же P3 с отдельным job'ом публикации.

- [Устаревшие SHA и `wrangler`] → обновлять правкой; Dependabot для действий — P3, если начнёт мешать.
- [Опечатка в SHA ломает workflow] → все workflow запускаются в этом PR (`check-*` по `paths:` — через правку самих файлов), деплой проверяется после merge.
