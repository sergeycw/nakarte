# Design

## Context

Зачем — [proposal](proposal.md). Решение владельца — [record-new-ui-decisions](../archive/2026-10-08-record-new-ui-decisions/design.md), «Сессии: только автосохранение»; что сессия старого клиента хранит — [ресёрч, п. 5](../../research/new-ui.md#последствия-удаления); формат ссылки выбирается здесь — [ресёрч, п. 6](../../research/new-ui.md#6-контракты-которые-новый-ui-держит). Модель разметки — [add-web-route-editor](../archive/2026-10-09-add-web-route-editor/design.md), «Разметка маршрута в треке»: `TrackData.routes[i]` — номера опорных точек в `segments[i]` и состояния отрезков между ними; `settledRoute` делает ожидающий отрезок без живого запроса непроложенным. Треки, `nktk` и ссылки — [add-web-tracks](../archive/2026-10-08-add-web-tracks/design.md).

Справочник старого клиента: сессии — [leaflet.control.sessions](../../../src/lib/leaflet.control.sessions/index.js), разметка — `serializeRouteMarkup`/`applyRouteMarkup` и `simplifyKeepingWaypoints` в [track-list.js](../../../src/lib/leaflet.control.track-list/track-list.js), почему запись на `pagehide` ненадёжна — [fix-route-markup-after-reload](../archive/2026-10-07-fix-route-markup-after-reload/design.md).

Что выяснилось при чтении кода (2026-10-09, `master` `c1d535a`):

- Сессия старого клиента — запись в IndexedDB `sessions` со строкой треков (`nktk`) и разметкой по координатам на сетке ~2.4 м; при загрузке линия упрощается заново, поэтому номера узлов нестабильны и разметка матчится по ключам координат. У нового приложения разметка — номера, значит, сохранять нужно ровно те точки, что в сторе.
- `prepareImport` выбрасывает `routes`: линии упрощаются (`normalizeLine`), номера опорных точек после этого неверны. `shareBody` упрощает линии перед `saveNktk` тем же допуском.
- Протобуф: и `pbf` 3.2.1 старого клиента (`readFields`: `if (this.pos === startPos) this.skip(val)`), и `pbf` 5.1.2 нового (`nextField` → `skip`) пропускают поле с незнакомым номером любого типа, кроме групп. Сгенерированный `nktk_pb.js` старого клиента читает в `Segment` только поля 1 и 2.
- Стор Zustand меняет `tracks` новым массивом на любую правку, неизменённые треки остаются теми же объектами; отрезки трека — неизменяемые массивы (`updateTrack` кладёт новые).
- Browser-тесты рендерят `App` много раз в одной странице: общий IndexedDB протёк бы между тестами.

## Goals / Non-Goals

**Goals:**
- Перезагрузка вкладки возвращает треки и разметку маршрута точно такими, какими они были, и не подвешивает страницу на большом треке.
- Ссылка несёт маршрут и остаётся читаемой старым клиентом и хранилищем без изменений.

**Non-Goals:**
- Список сессий, `sid=`, `BroadcastChannel`, переключение вкладок (решение владельца).
- Перенос последней сессии старого клиента — change переключения.
- История undo между перезагрузками (у старого клиента её тоже нет).
- Разметка в файлах GPX/KML.

## Decisions

Решения, которых нет в ресёрче, архивах и задаче change, помечены **[агент]**: владелец попросил не останавливаться на вопросах, они ждут его подтверждения.

### Ссылка: необязательное поле разметки в `nktk` версии 4 **[агент]**

Ресёрч оставлял два варианта: новая версия `nktk` или отдельный параметр адреса. Оба хуже третьего:

- Версия 5 — старый клиент отвечает на неё `CORRUPT` (`parseNktk` знает только 1–4), а требование задачи — хотя бы геометрия в старом клиенте.
- Отдельный параметр рядом с `nktl=` — разметку пришлось бы хранить вне тела хранилища (в адресе), либо менять тело и контракт `track-storage`; к тому же номера опорных точек надо связать с конкретными отрезками конкретного трека.

Выбрано: та же версия 4, в сообщении `Segment` — необязательное поле 3 с разметкой отрезка. Протобуф пропускает незнакомые поля (Context), поэтому старый клиент читает геометрию как раньше, а трек без разметки пишется байт в байт как раньше (поле не пишется). Тело хранилища — те же строки base64url через `/`, алфавит и лимит `track-storage` не меняются.

```proto
message Segment {
    repeated sint32 lats = 1;
    repeated sint32 lons = 2;
    SegmentRoute route = 3;           // новое; нет — отрезок без разметки
}
message SegmentRoute {
    repeated uint32 gaps = 1;         // waypoints[i+1] − waypoints[i] ≥ 1; первая опорная — точка 0
    repeated uint32 legs = 2;         // 0 — прямой; 2k+1 — проложен активностью activities[k]; 2k+2 — непроложенный
    repeated string activities = 3;   // id активностей отрезка без повторов (hiking, mtb …)
}
```

- Ожидающий отрезок пишется непроложенным (`settledRoute`): ответ на прежний запрос к открытой ссылке не придёт.
- Разметка негодна (сумма шагов не равна числу точек − 1, у прямого или непроложенного отрезка шаг больше 1, код вне таблицы активностей) — у этого отрезка её нет, геометрия открывается. Незнакомая активность остаётся строкой: прокладка с ней даст ошибку `unknown activity`, как у сохранённой в редакторе.
- Номер поля и коды — в `web/src/tracks/nktk.proto` (копия схемы старого клиента с новым полем), запись и чтение — руками в `nktk.ts`, как остальное.

### Упрощение линии не трогает опорные точки

`simplifyRouted(points, route)` в `routing/line.ts` (аналог `simplifyKeepingWaypoints` старого клиента): линия разворачивается через 180° целиком (`unwrapLine`, число точек не меняется), затем каждый проложенный отрезок упрощается отдельно вместе со своими опорными концами, у прямого и непроложенного промежуточных точек нет; номера опорных точек пересчитываются. Отрезок без разметки упрощается как раньше. Применяется в двух местах:

- `shareBody` — перед `saveNktk`;
- `prepareImport` — при открытии ссылки (сейчас он разметку выбрасывает).

Координаты в `nktk` всё равно округляются по сетке ~2.4 м; две опорные точки ближе шага сетки остаются двумя точками — упрощение их не склеивает, потому что опорные концы не участвуют в отсеве по радиусу.

### Автосохранение: структура в IndexedDB, а не строка `nktk` **[агент]**

База `nakarte-web` (своё имя на общем origin, `sessions` старого клиента не открывается), версия 1, хранилище объектов `autosave`, одна запись под ключом `tracks`:

```ts
{ version: 1, tracks: { name, color, visible, measureTicksShown, points: Waypoint[],
                        segments: Float64Array[] /* lat, lng подряд */, routes: (SegmentRoute | null)[] }[] }
```

- Точные координаты, без округления и упрощения: номера разметки верны как есть, и «Опорная точка на прямой» больше не пропадает. Строка `nktk` дала бы сетку 2.4 м и заставила бы упрощать с опорными точками на каждой записи.
- Отрезки — `Float64Array`: structured clone типизированного массива — копия буфера, а не обход 100 тыс. объектов `{lat, lng}`. Замер — «Проверки».
- Разметка пишется через `settledRoute` и при чтении проверяется так же, как в ссылке (`routeFits`); негодная — `null`, трек открывается ломаной.
- Запись с другим `version` или испорченная — пропускается, следующая запись её перезапишет.

### Когда писать **[агент]**

На каждое изменение `tracks` в сторе, без таймера: если записи нет в полёте — новая транзакция сразу; если есть — пометка «грязно» и ещё одна запись последнего состояния после её `complete`. Серия правок (рисование, ответы роутера) даёт не больше одной записи на время коммита, а одиночная правка уходит в базу сразу, а не через окно debounce, в которое укладывается перезагрузка. На `pagehide` при «грязном» состоянии запись стартует немедленно, не дожидаясь текущей: транзакции `readwrite` над одним хранилищем IndexedDB выполняет в порядке создания. Доходит ли она при перезагрузке — не гарантировано (подвох из `AGENTS.md`), поэтому основная гарантия — запись по изменению.

### Восстановление и треки из адреса **[агент]**

- При старте `App` открывает базу и читает запись до того, как добавит хоть один трек из адреса или файла: действия списка (`createTrackActions`) ждут промис восстановления перед `addTracks`. Восстановленные треки встают в начало списка (на случай, если трек успели создать до конца чтения), из адреса — после них; вид карты восстановление не меняет, `fitBounds` — только по трекам из адреса без `m=`, как раньше.
- Запись начинается только после восстановления: иначе пустой стор первой записью затёр бы сохранённое. Если до конца чтения список изменился — сразу одна запись.
- База не открылась (запрет хранилища сайта, ошибка) — предупреждение в консоли, приложение работает без сохранения, без тоста: пользователю нечего с этим делать. Испорченная запись тоже только предупреждение: восстановление её пропускает, сохранение работает и заменит её.
- База не ответила за 3 с (`RESTORE_TIMEOUT_MS`) — треки из адреса и файлов отпускаются, не дожидаясь чтения; если оно потом придёт, восстановленные треки встанут в начало, а запись включится только после него.
- Стор восстанавливается один раз: Fast Refresh в dev перезапускает эффекты `App` при живом сторе, и второе чтение задвоило бы список.
- Повтор ссылки при сохранённом списке даёт дубль трека — как повторное открытие ссылки в старом клиенте внутри одной сессии; без сравнения треков.

### Несколько вкладок **[агент]**

Рабочий набор один на origin: каждая вкладка пишет свой список целиком, последняя запись выигрывает. Вкладка пишет только когда меняется её список, так что фоновая вкладка без правок чужое не затирает; затирает — если в ней что-то поменялось (например, пришёл ответ роутера). Синхронизация между вкладками — это `BroadcastChannel`, который владелец убрал; риск — в «Risks».

### Редактор после восстановления

Восстановленный трек — новые массивы отрезков, `WeakMap` редакторов (`routing/editing.ts`) их не знает, и при входе в редактирование создаётся новый редактор из `fromSegment(points, route)` с пустой историей — как после разворота трека. Отдельной связи с автосохранением редактору не нужно: запись идёт по `tracks`, который редактор и так обновляет на каждую правку и ответ.

### Модули

- `web/src/autosave/saved.ts` — трек ↔ запись (чистые функции, unit).
- `web/src/autosave/autosave.ts` — `startAutosave(store, storage)`: восстановление, подписка, запись без таймера, `flush` (unit на хранилище в памяти с ручными промисами); `pagehide` и `visibilitychange` вешает `App`.
- `web/src/autosave/idb.ts` — `indexedDbStorage(name)`: `load()`/`save(record)` над IndexedDB (browser mode, настоящий IndexedDB Chromium).
- `App` получает проп `autosave` (хранилище или `null`); по умолчанию — IndexedDB `nakarte-web`. `renderApp` по умолчанию даёт каждому рендеру своё хранилище в памяти — browser-тесты не видят чужих треков; тесты автосохранения передают IndexedDB с уникальным именем базы.

### Тесты

IndexedDB в Node нет (Node 22 и 24 его не реализуют), а `fake-indexeddb` — ещё одна зависимость только для тестов, которая проверяет не тот IndexedDB, что в браузере. Поэтому хранилище — параметр: логика автосохранения проверяется unit-тестами на хранилище в памяти, а модуль IndexedDB — browser mode в Chromium **[агент]**.

- **Unit:** `nktk.test.ts` — запись и чтение разметки, «Ссылка без маршрута» (строка совпадает с прежней), негодная разметка, ожидающий отрезок; `line.test.ts` — `simplifyRouted` (опорные точки на месте, номера пересчитаны, через 180°); `import-result.test.ts` и `share.test.ts` — разметка проходит ссылку; `saved.test.ts` — трек → запись → трек; `autosave.test.ts` — восстановление до треков из адреса, запись после восстановления, одна запись в полёте, `pagehide`, ошибка хранилища.
- **Browser mode:** `idb.browser.test.ts`; `Autosave.browser.test.tsx` — сценарии спек `route-editing` («Перезагрузка страницы», «Последний отрезок трека», «Конец рисования по Escape», «Трек после undo и redo», «Разворот трека», «Опорная точка на прямой», «Перезагрузка во время прокладки») и `tracks` («Список после перезагрузки», «Удалённый трек», «Хранилище недоступно») — «перезагрузка» — размонтировать `App` и отрендерить заново с той же базой; «Открытие ссылки» — `nktk=` с разметкой.
- **e2e:** настоящая перезагрузка страницы со сборкой клона и заглушкой движка: «Перезагрузка страницы», «Ссылка при сохранённом списке», «Сессия старого клиента» (запись в базу `sessions` до загрузки остаётся), «Открытие ссылки» через «Copy link» и хранилище в памяти фикстуры.
- «Ссылка в старом клиенте» — разово: строка с разметкой, прочитанная `nktk_pb.js` старого клиента с его `pbf` 3.2.1, итог в «Проверки»; старый клиент заморожен и тестами нового не гоняется.

### Время и память

Сценарий из задачи: трек на 100 тыс. точек и маршрут на сотни точек — время записи (синхронная часть на главном потоке: подготовка записи и `put`) и чтения при старте, замер в browser mode; `phys_footprint` — если картина памяти меняется (запись держит `Float64Array` только на время транзакции). Итог — «Проверки».

### Выяснилось при apply

- `cleanup()` из `vitest-browser-react` асинхронный (`Promise<void>`, `pure.d.ts`): без `await` следующий `render` того же теста упирается в «overlapping act() calls», и карта второго `App` не загружается. Существующие тесты зовут его без `await` в `afterEach` — там это не мешает, в «перезагрузке» внутри теста мешает.
- `App` при размонтировании дописывает несохранённое (`flush`, как на `pagehide`): browser-тесты так «перезагружают» приложение, а тест ждёт записей хранилища, прежде чем рендерить заново.
- e2e «Ссылка готова» (add-web-tracks) открывал ссылку во второй вкладке того же контекста — теперь там треки из ссылки добавляются к автосохранённым, и трек в списке дважды. Ссылку открывает другой контекст браузера (другой пользователь со своим IndexedDB): фикстура `network` получила `attach(context)` — тот же перехват сети и то же хранилище треков в памяти для второго контекста.
- e2e ждёт, пока запись дойдёт до базы `nakarte-web` (читает её из страницы), и только потом перезагружает: иначе перезагрузка обгоняет транзакцию — ровно тот подвох `pagehide`, от которого запись сразу по изменению и защищает, но в тесте это гонка.
- **Ревью диффа (субагент, 2026-10-09) и исправления.** Запись базы с мусором в разметке (`legs: [null]`) бросала исключение посреди восстановления: обещание восстановления отклонялось, треки из адреса и файлов ждали его вечно, сохранение не включалось — теперь форма разметки проверяется (`isRouteShape`), разбор записи — в `try`, `App` отпускает треки в `finally`. Молчащий `indexedDB.open` держал бы ссылку вечно — таймаут 3 с. Fast Refresh задваивал список — восстановление один раз на стор. Битое поле разметки в `nktk` (не тот тип, оборванное число) делало весь трек `CORRUPT`, хотя старый клиент его открывает, — поле разбирается отдельно, при ошибке отрезок без разметки. Разметка из одних прямых (чужой ввод) принималась и писалась в ссылку — `routeFits` требует хотя бы один отрезок с активностью, как `toSegment`. Ошибка транзакции IndexedDB уходила в предупреждение как `null` — отказ только по `abort`.
- Помощники мыши и клавиатуры browser-тестов редактора вынесены из `RouteEditor.browser.test.tsx` в `web/src/test/map-events.ts`: ими пользуются и тесты автосохранения.

## Проверки

### Ссылка в старом клиенте

2026-10-09: `parseNktkSequence` старого клиента (`src/lib/.../parsers/nktk.js` с `nktk_pb.js` и `pbf` 3.2.1 из корневых `node_modules`, собранный `rolldown` вне репозитория) прочитал строку с разметкой (`saveNktk` нового приложения, отрезок из четырёх точек с отрезками `hiking` и непроложенным `mtb`) и ту же строку без разметки одинаково: те же название, точки отрезка и точка трека, без ошибки.

### Время записи и чтения

2026-10-09, Vitest browser mode (Chromium 156 headless), временный тест вне репозитория, настоящий IndexedDB: трек на 100 тыс. точек (случайное блуждание) и маршрут на 600 точек с шестью проложенными отрезками, пять прогонов.

| | запись в Float64Array (выбрано) | объекты `{lat, lng}` (для сравнения) |
|---|---|---|
| подготовка записи (`toSaved`) | 0.3–2.3 мс | — |
| `put` до `complete` транзакции | 1.2–3.1 мс | 9.8–11.1 мс |
| чтение (`get`) | 0.5–0.7 мс | 13–29 мс |
| разбор записи (`fromSaved`) | 0.4–2.6 мс | — |

Запись и чтение большого набора укладываются в несколько миллисекунд и главный поток не подвешивают; кешировать упакованные отрезки между записями незачем. Память: запись живёт только до конца транзакции, постоянных копий нет, поэтому картина памяти вкладки не меняется, и `phys_footprint` не мерили.

## Risks / Trade-offs

- [Две вкладки с правками: последняя запись затирает список другой] → вкладка без правок не пишет; синхронизации нет по решению владельца; при переключении на `/` можно вернуться к вопросу.
- [Запись на `pagehide` при перезагрузке может не дойти] → основная запись — сразу по изменению, без debounce.
- [Незнакомое поле в `nktk` — неявный контракт со старым клиентом] → проверено на его коде; старый клиент заморожен и удаляется в change переключения.
- [Опорных точек тысячи (импортированная ломаная, к которой дорисовали маршрут): разметка в ссылке — байт на точку] → упакованные `uint32`, шаг 1 — один байт; лимит хранилища 2 МиБ.
