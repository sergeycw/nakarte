# Design

## Context

Мотивация — в `proposal.md`. Клиент: `src/lib/leaflet.layer.elevation-display/index.js` (`maxNativeZoom: 11`, `noDataValue: -512`, `decodeElevations` — префиксная сумма Int16; `404` — нет данных; выше z11 клиент сам интерполирует четыре соседних пикселя). Тайлы автора проверены 2026-10-07: 131 072 байта после распаковки, `Content-Encoding: gzip`, `Access-Control-Allow-Origin: *`, `Cache-Control: max-age=86400`, `Content-Type: image/png` (тело при этом не PNG), `404` на z12 и над океаном.

Данные — перепакованные куски DEM 3″ viewfinderpanoramas в бакете `nakarte-elevation` (`dem3/<градус>`, формат — в архиве `add-elevation-api`). Генератор автора [wladich/elevation_tiles_for_nakarte](https://github.com/wladich/elevation_tiles_for_nakarte) строит тайлы из тех же HGT.

## Контракт тайлов автора

Генератор автора — GDAL: `prepare_raster.sh` (значения ниже −430 → nodata −512, обрезка по ±85.06°, `gdalwarp -t_srs EPSG:3857 -r bilinear` в растр 524 288 × 524 288 = z11), затем `gdaladdo -r gauss` (обзоры z0–10) и `geotiff2mbtiles.py` (дельта, gzip −6, пустые тайлы не пишутся). Повторил расчёт на Rust поверх наших `dem3` и сверил с живыми тайлами 2026-10-07, совпадение побайтное:

- **z11.** Высота в центре пикселя Web Mercator — билинейно по четырём узлам сетки 3″. Узлы без данных (войды `-32768` и значения ниже −430) исключаются, веса остальных нормируются на их сумму (`GWKBilinearResample4Sample`). Если без данных ближайший к центру узел, пиксель −512: `GWKGeneralCaseThread` проверяет валидность только исходного пикселя, в который попала точка («ignores the multi-pixel input of bilinear»). Округление `floor(v + 0.5)` (`GWKRoundValueT`). Узел на стыке градусов есть в двух HGT, и значения там расходятся (общая строка `N42E044`/`N43E044` — в 812 узлах из 1204, столбец `N42E044`/`N42E045` — в 170); автор склеивал HGT в один растр, и на стыке остался файл, последний по алфавиту имени: `N43` поверх `N42`, `E045` поверх `E044`, `S34` поверх `S33`, `W071` поверх `W070` (сверено на 11/1277/752, 11/1280/755, 11/625/1222, 11/625/1223, 11/580/1023: с правилом «первый» — от 4 до 335 пикселей разницы, с правилом «последний» — 0). Проверено на 11/1277/754 (Казбек), 11/1260/763 (Батуми), 11/1225/835 (Мёртвое море, 46 пикселей у войдов): 65 536 из 65 536.
- **z0–10.** Каждый уровень — из предыдущего (`GDALRegenerateCascadingOverviews`: каскад для `gauss` при nodata-маске). Ядро 3×3 с весами 1-2-1 по осям, окно смещено: пиксель `i` берёт `2i, 2i+1, 2i+2` уровня ниже (`GDALResampleChunk32R_Gauss` при коэффициенте 2). Пиксели без данных и за краем растра пропускаются, вес нормируется; среднее приводится к float32 и округляется от нуля (`GDALCopyWord<float, short>`: `v ± 0.5f`). Проверено на z10 (Казбек, Батуми, Баку с отрицательными высотами, Мёртвое море), 5/21/11, 1/0/0, 0/0/0: 65 536 из 65 536.

Спека в первой редакции требовала «центр пикселя без усреднения» на всех зумах — это расходилось с автором и исправлено.

## Goals / Non-Goals

**Goals:**
- Формат и значения автора без правок клиента.
- Без миллионов объектов в R2 и без архива, который не помещается на диск раннера.

**Non-Goals:**
- Терраин-тайлы в форматах terrarium или Terrain-RGB.
- Отмывка рельефа (hillshade).

## Decisions

### z0–9 заранее, z10–11 на лету

Объём (2026-10-07): тайлов с данными (по 26 157 градусам в R2, сверху) — z11 ≤ 2.01 млн, z10 507 тыс., z9 129 тыс., z0–8 46 тыс.; средний тайл автора в gzip по выборке 300 случайных — z11 12.9 КБ (медиана 3.6), z10 16.9 КБ (медиана 6.4). Пирамида целиком ≈ 38 ГБ — больше диска раннера (14 ГБ) и локального; z0–9 ≈ 3.5 ГБ.

Поэтому архив в R2 содержит только z0–9, а z10–11 Worker считает по запросу из кусков `dem3`: тайл z11 — 256×256 пикселей из 1–4 кусков, z10 — 513×513 пикселей z11 и сглаживание, до 9 кусков. Расчёт пикселя — один код в `core` для генератора и для Worker, так что уровни на лету и из архива согласованы по построению.

Альтернативы: вся пирамида в одном архиве — потоковая составная загрузка в R2 с частями одинакового размера или шарды, ≈ $0.57 в месяц; z0–8 в архиве и z9–11 на лету — экономит ~2.5 ГБ (≈ $0.04 в месяц), но z9 на лету — до 25 кусков и ~1 млн пикселей на запрос.

### Формат архива: плотный индекс

Объект `tiles/elevation-z0-9` в бакете `nakarte-elevation`: заголовок 8 байт (magic `NKT1`, `u8` максимальный зум, 3 байта нулей), затем индекс по всем позициям z0–9 — `(4^z − 1) / 3 + y · 2^z + x`, 349 525 записей по 12 байт (`u64` смещение и `u32` длина, LE, ≈ 4.2 МБ), затем тела тайлов (уже в gzip). Длина 0 — тайла нет.

Тайл читается двумя range-запросами: страница индекса из 256 записей (3 072 байта, в кеше изолята соседние тайлы попадают в одну страницу) и тело. Почему не PMTiles: директории PMTiles сжаты и многоуровневые, в wasm пришлось бы писать их разбор; плотный индекс для z0–9 занимает 4 МБ и читается арифметикой. После перезаливки архива Worker нужно передеплоить: кеш изолята мог держать страницы индекса старой версии.

### Маршрут и заголовки

Тот же Worker `nakarte-elevation`, `GET /tiles/{z}/{x}/{y}`: данные, бакет и деплой общие. Отличия от API высот:
- CORS — `Access-Control-Allow-Origin: *` без проверки `Origin`, как у автора (API — список origin с `credentials`); тайлы запрашиваются без `withCredentials`.
- Тело — байты в gzip, `Content-Encoding: gzip`; в Worker ответ создаётся с `encodeBody: "manual"` (`EncodeBody::Manual` в `workers-rs`), иначе рантайм сожмёт уже сжатое тело ещё раз.
- `Content-Type: application/octet-stream`, а не `image/png` автора: клиенту тип не важен (`responseType: 'arraybuffer'`).
- `Cache-Control: max-age=86400`. Cache API на `*.workers.dev` не работает, поэтому повторные запросы кеширует браузер, а куски `dem3` и страницы индекса — память изолята (`ByteCache` из `add-elevation-api`).

### Генератор

Крейт `tiles` (`elevation-tiles`): читает `dem3` с диска и пишет архив. Мир обрабатывается блоками по тайлу z5: для блока считается растр z11 со сторожевой полосой (16 447 пикселей вместо 16 384, чтобы каскад до z5 не выходил за блок), полосами по 1024 строки параллельно; из него каскадом z10…z5, тайлы z5–9 блока сжимаются gzip −6 и дописываются в архив; тайл z5 кладётся в мировой растр z5 (8192², 128 МБ), из которого в конце строятся z0–4. Блоки без градусов пропускаются.

Генерация всего мира — ручной workflow `elevation tiles`: раннер освобождает диск от предустановленных SDK, скачивает весь `dem3/` через S3 API R2 (13.1 ГБ), строит архив и заливает его одним объектом тем же токеном, что `elevation data` (Object Read & Write на `nakarte-elevation`), новый токен не нужен. `workflow_dispatch` запускается только из `master`.

## Тесты

- `core`: кодирование тела (обратное `decodeElevations`), сглаживание на синтетике (краевые случаи: nodata, край мира), формат архива (запись и чтение), правило ближайшего узла.
- Контрактный тест, допуск — точное совпадение: эталоны автора `fixtures/tiles/{z}_{x}_{y}` (как отдаёт `tiles.nakarte.me`, в gzip) — z11 Казбек, Эльбрус, Батуми, Мёртвое море (войды), стыки градусов 11/1277/752 (N42/N43) и 11/625/1222, 11/625/1223 (W070/W071, S33/S34), 11/1223/752 в Чёрном море (край покрытия по 43° с.ш.: вода 0 и −512), z10 Казбек — сравниваются с тайлами на лету поверх прореженных `fixtures/dem3/*` (`elevation-tiles thin`); четыре тайла z1 автора, сглаженные в z0, сравниваются с z0 автора (край мира, отрицательные высоты); тайл над океаном — `404`. Первый прогон 2026-10-07: все 65 536 пикселей каждого тайла совпали, допуск — точное совпадение.
- `server`: маршрут тайлов поверх фикстур.
- `worker`: `vitest` в `workerd` — заголовки, `404` (z12, океан, кривой путь), тело z11 на лету совпадает с эталоном, тайл z0–9 читается из архива-фикстуры в локальном R2.

## Регион

2026-10-07, локально (M-серия, 11 потоков), Кавказ `--bbox 40,41,47,45` по 29 градусам `dem3` (широта 41–44°, долгота 40–46°): 2 блока z5, 164 тайла z0–9 (6.1 МБ тел, архив 10.3 МБ вместе с индексом 4.2 МБ), 3.4 с, пик памяти 1.5 ГБ. Тайлы z8–9 внутри региона (9/319/188, 9/316/187, 9/320/189, 9/314/186, 9/318/190, 8/159/94, 8/158/93, 8/157/93) совпали с автором побайтно; z7 и ниже у края региона расходятся — соседних градусов в регионе нет.

`wrangler dev` (локальный `workerd`, wasm, локальный R2): тайл z11 на лету — 10–19 мс на запрос, z10 — 15–21 мс, z9 из архива — 3 мс; тело уходит в gzip один раз (65 348 байт → 131 072). Клон на 8766 с `elevationTileUrl` на 8789: над Казбеком на z5, z9, z10 и z14 высота показывается, на z14 — с уклоном; запросы тайлов — только к 8789.

## Risks / Trade-offs

- [CPU Worker на тайл z10–11 на лету] → оценка ~15–30 мс в wasm, замер после деплоя — в этот файл; на Workers Paid 30 млн CPU-мс в месяц включены.
- [Обновление `dem3` без перегенерации архива] → z10–11 сразу на новых данных, z0–9 — после ручного прогона `elevation tiles`.
- [Расхождение на равенстве `dx = 0.5` ровно] → у GDAL ближайший пиксель при равенстве — южный, у нас — северный; на реальных координатах не встречается.

## Migration Plan

Регион локально → маршрут в Worker и тесты → merge и деплой Worker → прогон `elevation tiles` для мира → `elevationTileUrl` в `config-target/clone.js`. Отката на автора нет: клона нет в продакшене.
