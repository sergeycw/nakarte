# Design

## Context

Мотивация — в `proposal.md`. Три Worker'а на `*.nakarte-routing.workers.dev`, своего домена и зоны нет, поэтому правила WAF и rate limiting на уровне зоны недоступны — только внутри Worker'а.

Нагрузка за 6 дней до 2026-10-07 (аналитика `workersInvocationsAdaptive`, трафик почти весь проверочный):

| Worker | запросов | CPU p50 | CPU max |
|---|---|---|---|
| `nakarte-elevation` | 218 | 3 мс | 3.8 с |
| `nakarte-tracks` | 21 | 0.6 мс | 2.3 мс |
| `nakarte-cors-proxy` | 34 | 0.6 мс | 1.8 мс |

3.8 с — сверка API на 3000 случайных точках по миру в одном запросе: тысячи кусков `dem3`; профили и тайлы на лету на два-три порядка дешевле.

Через прокси, кроме импорта треков и поиска, постоянно идут тайловые слои: тепловые карты Strava, «Mountains by Aleksey Tsvetkov», швейцарская топокарта, wikimapia (`src/layers.js`), а при печати — растеризация этих слоёв.

## Goals / Non-Goals

**Goals:**
- Один IP не может в одиночку разогнать счёт.
- Зависший или неожиданно тяжёлый запрос обрывается задолго до 30 с.

**Non-Goals:**
- Защита от распределённой атаки: с тысяч IP лимит по IP не спасает, на это — budget alerts и ручное отключение `workers.dev`.
- Ограничение частоты в адаптере `server` (VPS): там свой сервер и своя защита.

## Decisions

### Частота — привязка Workers Rate Limiting

`[[ratelimits]]` в `wrangler.toml` (GA с 2025-09-19), `limit` за `period = 60`. Счётчики локальны для машины и локации Cloudflare и приблизительны — документация прямо говорит не использовать их для точного учёта; для защиты от одного клиента этого хватает. Альтернативы: Durable Object со счётчиком — точный, но лишний запрос и задержка на каждый тайл; KV — запись на каждый запрос дороже самого запроса.

Отдельный `namespace_id` на группу: `1001` — тайлы высот, `1002` — API высот, `1003` — треки, `1004` — прокси. Ключ — `CF-Connecting-IP`; без него (локальный `wrangler dev`, тесты) лимит не применяется.

Цифры за минуту: тайлы высот — 600 (экран 4K на z10–11 — ~135 тайлов, быстрая прокрутка — сотни), API высот — 60 (профиль трека — один-два запроса), треки — 60, прокси — 1200. Для прокси согласовывалось 600, поднято до 1200: оверлей Strava при прокрутке плюс печать большой карты дают сотни тайлов в минуту через прокси, а CPU на запрос прокси — ~1 мс.

### Порядок проверок

Сначала проверка `Origin` (у API высот, треков, прокси), потом частота: запрос с чужого `Origin` получает `403` и не тратит счётчик, а `429` всегда отдаётся с CORS-заголовками, и клиент видит статус вместо сбоя CORS. `Retry-After: 60` — по длине окна.

В `nakarte-elevation` решение «какой счётчик и надо ли считать» и ответ `429` — в `core` (`http`), чтобы CORS-логика была в одном месте; вызов привязки — в адаптере `worker` (`Env::rate_limiter` из `workers-rs` 0.8). В JS-воркерах — прямо в `fetch`.

### Потолок на вызов

`[limits]` в `wrangler.toml`: `cpu_ms` — с запасом от наблюдённого максимума (elevation 10 000 мс при 3.8 с максимуме; tracks и прокси 500 мс при 2 мс). `subrequests`: tracks — 10 (одно `head`/`put`/`get` R2), прокси — 50 (один `fetch`, редиректы клиент проходит сам: `redirect: 'manual'`). Для elevation не задаётся: запрос на 10 000 точек вразброс законно делает тысячи чтений R2 (см. риск в архиве `add-elevation-api`), а снижение превратило бы его в `500`.

### Тесты

`vitest` + `@cloudflare/vitest-pool-workers` в `workerd`: miniflare эмулирует `ratelimits`, а `vitest.config.js` переопределяет лимиты на маленькие (`miniflare.ratelimits`), чтобы `429` проверялся десятком запросов. Тест задаёт `CF-Connecting-IP` сам; прочие тесты его не шлют и под лимит не попадают. `cors-proxy` получает тесты впервые — по шаблону `workers/tracks` (свой `package.json`, `.npmrc`, `check-cors-proxy.yml`); апстримный запрос подменяется `outboundService` miniflare, сеть не нужна. `[limits]` в тестах не проверяется — это настройка платформы, её проверяет деплой (`wrangler deploy` валидирует конфиг).

## Risks / Trade-offs

- [Слишком тесный лимит ломает обычное использование] → цифры с запасом от сценариев выше; `429` виден в аналитике Workers (статус ответа), при жалобах — поднять в `wrangler.toml`.
- [Цена привязки Rate Limiting в документации не указана] → после деплоя проверить «Billable usage» в дашборде; budget alerts на $3 настроены.
- [Пользователи за одним NAT делят лимит] → для клона с единицами пользователей несущественно.

## Migration Plan

Merge → деплой из `deploy-pages.yml` (конфиги с `[limits]` и `[[ratelimits]]`) → проверка `curl` с проды: обычный запрос `200`, заголовков лимита нет. Откат — убрать блоки из `wrangler.toml` и передеплоить.
