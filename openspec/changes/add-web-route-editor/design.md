Что выяснилось при чтении старого кода (2026-10-09, `master` `f9b715a`):

- Модель старого редактора — плоский массив узлов Leaflet, где точка маршрута — узел со ссылкой `_routeLeg` на общий объект отрезка, а опорная — без неё. Устаревший ответ отсекается тем, что все узлы между концами всё ещё ссылаются на объект именно этого запроса. Временный узел под курсором и `_drawingDirection` сдвигают индексы (`_fixedNodesRange`) — следствие модели Leaflet, в новой модели их нет ([ресёрч](../../research/new-ui.md#редактор-маршрута-поверх-карты)).
- Снимок истории — JSON узлов с активностью и ожидающих отрезков; восстановление отменяет все запросы и перезапрашивает ожидающие. Запись одинакового снимка пропускается.
- `buildSegmentNodes`: упрощение с допуском `360 / 2^24`°, затем отбрасываются крайние точки ближе 20 м к своим опорным; пустой или одноточечный ответ — ошибка `empty route`. Ошибка `datafile … not found` превращается в `no routing data for this area`.
- Разворот трека в старом клиенте пересоздаёт отрезки из голых координат, то есть разметка теряется до перезагрузки и восстанавливается только сопоставлением по координатам (`applyRouteMarkup`, оба направления).
- Проверка живости серверного BRouter — `GET /brouter` без параметров: любой HTTP-ответ (обычно `404`) — жив, сетевая ошибка — нет.

MapLibre 6.13 (исходники `web/node_modules/maplibre-gl/src/`): `preventDefault()` у события карты `mousedown` выключает перетаскивание карты, у `dblclick` — зум двойным кликом, у `touchstart` — жесты пальцами (`ui/events.ts`, `ui/handler/map_event.ts`). `setStyle` с diff сравнивает источники `deepEqual` без проверки на одинаковую ссылку (`style-spec/src/util/deep_equal.ts`): каждое обновление стиля обходит данные всех GeoJSON-источников. `@vis.gl/react-maplibre` 8.1 даёт `useMap()` детям `<Map>` и компонент `<Marker>` с HTML-содержимым.

## Goals / Non-Goals

**Goals:**
- Модель редактора, которую unit-тесты проверяют по сценариям спек `routing` и `route-editing` без карты и сети.
- Разметка маршрута в треке в виде, который change 6 запишет в ссылку и IndexedDB как есть.

**Non-Goals:**
- Разметка в ссылках, экспорте и автосохранение (change 6): ссылки и файлы по-прежнему несут только геометрию.
- Правка линии вне маршрута и точки трека — новый change (ниже, «Что входит»).
- Перестроение маршрута во время перетаскивания, настройки активности (SAC, высоты) — backlog «Редактор и активности».
- Полировка вида панели редактирования и маркеров — change `polish-web-ui`.

### Что входит в этот change **[владелец]**

Инвентаризация ([п. 5](../../research/new-ui.md#5-инвентаризация-функций)) переносит и «Правку линии» (Cut, Join, Shortcut, удалить сегмент, новый трек из сегмента), и «Точки» (переименовать, переместить, скопировать координаты, удалить, добавить), но в таблице changes им нет места. Здесь — то, без чего редактор не работает: рисование, опорные точки, прокладка, undo/redo, «New track» и «Add segment» (новый отрезок с рисованием, как кнопка старого клиента). Остальное — новый change `add-web-line-tools` (контекстное меню опорной точки и линии, Join и Shortcut с выбором на карте, точки трека), строка «6б» в таблице ресёрча: после автосохранения, до переключения. Причина: change 5 и так самый большой (5–7 дней), а инструменты линии опираются на модель редактора, но не меняют её.

### Модель линии — опорные точки и отрезки, а не плоский массив

`web/src/routing/line.ts`, неизменяемые данные:

```ts
type Leg =
  | { state: 'straight' }
  | { state: 'routed'; activity; points: LatLng[] }   // точки между опорными, без концов
  | { state: 'pending'; activity; request: number }
  | { state: 'failed'; activity };
interface RouteLine { waypoints: LatLng[]; legs: Leg[] }  // legs.length = waypoints.length − 1
```

Отрезок трека — `waypoints[0], legs[0].points…, waypoints[1], …`; ожидающий и непроложенный отрезки — прямые без промежуточных точек. Устаревший ответ — тот, чей `request` больше не лежит ни в одном ожидающем отрезке: перетаскивание, удаление, undo заменяют отрезок новым объектом, и ответ молча отбрасывается — это требование «Устаревшие ответы отбрасываются» без сравнения узлов. Отвергнуто: плоский массив с меткой отрезка у каждого узла, как у старого клиента, — индексы опорных точек приходится искать обходом, а временный узел под курсором и направление рисования сдвигают их.

### Разметка маршрута в треке

`TrackData.routes?: (SegmentRoute | null)[]` рядом с `segments`, по одной на отрезок: `SegmentRoute = { waypoints: number[]; legs: LegMark[] }` — номера опорных точек в отрезке и состояние каждого отрезка между ними без точек (`straight`, или `routed`/`pending`/`failed` с активностью). Геометрия остаётся в `segments`: длина, экспорт, ссылки и профиль работают с ней, как раньше. `fromSegment(points, route)` собирает `RouteLine` (без разметки каждая точка — опорная, все отрезки прямые, как правка импортированной линии в старом клиенте), `toSegment(line)` — обратно.

- Номера, а не координаты: change 6 сам выбирает формат ссылки (новая версия `nktk`), и опорные точки обязаны пережить его упрощение — тогда номера стабильны, а сопоставление по координатам (`applyRouteMarkup`) не нужно.
- Стор: `updateTrack` с новыми `segments` без `routes` сбрасывает разметку — любое действие, которое не знает о ней, не оставит номера, указывающие не туда. Разворот переворачивает разметку (номер `i` → `n − 1 − i`, отрезки в обратном порядке), дублирование и «новый трек из видимых» копируют её, импорт (`prepareImport` упрощает линии) её не несёт.

### Редактор — модель с очередью и историей

`web/src/routing/editor.ts`: `createRouteEditor(line, { route, onChange })` над одной линией. Правки: `addWaypoint(end, latlng, activity | null)`, `removeEndWaypoint(end)`, `moveWaypoint(i, latlng)`, `removeWaypoint(i)`, `insertWaypoint(leg, latlng)`, `undo`, `redo`, `dispose`. Каждая правка, кроме перетаскивания только что вставленной точки, кладёт прежнюю линию в историю (до 100 шагов, redo очищается); правка без изменений историю не трогает.

- Новый отрезок к поставленной точке: активность меню — `pending` с новым номером запроса, «Off» или Alt — `straight`.
- Перетаскивание: соседние отрезки с активностью (`routed`, `pending`, `failed`) — заново со своей активностью, прямые остаются прямыми; запросы старых отрезков отменяются (`AbortController`, движок снимает их из очереди).
- Удаление средней точки: один отрезок между соседями с активностью левого, иначе правого соседнего отрезка, без активности — прямой. Крайняя точка уходит со своим отрезком.
- Вставка на отрезок: внутри проложенного отрезка точки делятся по ближайшему к клику звену, обе половины остаются проложенными со своей активностью — геометрия не меняется, пока точку не сдвинули.
- Ответ: `routed` с точками или `failed` с ошибкой наружу (уведомление делает связь со стором); отменённый запрос молча отбрасывается.
- Undo/redo: отменить все запросы, восстановить снимок, у каждого `pending` в нём — новый запрос.

Роутер — параметр (`(from, to, activity, signal) => Promise<LatLng[]>`), поэтому очередь, отмена и устаревшие ответы проверяются unit-тестами на поддельном роутере с ручными промисами.

### Прокладка: запрос, ответ, движок или сервер

`web/src/routing/brouter.ts` — перевод старого `lib/brouter`: шесть активностей с профилями, запрос (`lonlats`, `profile`, `profile:path_preference=20`, `alternativeidx=0`, `format=geojson`), разбор GeoJSON в точки отрезка (упрощение функцией треков из `tracks/geometry.ts`, отсев крайних ближе 20 м), тексты ошибок. Долгота точки за ±180° (копии мира MapLibre) уходит в запрос приведённой, а ответ сдвигается обратно на те же 360°·k.

`web/src/routing/router.ts` — `createRouter`: при `routingEngine: 'browser'` — `routeInEngine` (отказ запуска `EngineStartError` → «роутер недоступен»), при `'server'` — `fetch(routingServer + '/brouter?…')` с тем же сигналом (сетевая ошибка → недоступен, ответ с ошибкой → текст ответа). Там же прогрев (`startEngine`, только движок в браузере), проверка живости (движок — не `failed`; сервер — `GET /brouter`, любой HTTP-ответ, таймаут 3 с) и состояние движка для кнопки (`status`/`subscribe`; у сервера всегда «готов»). Движок создаётся лениво: при выключенной прокладке рантайм не грузится.

Выбор активности — `localStorage` под ключом `nakarte-web:routing-activity` **[владелец]**; пока его нет, читается ключ старого клиента `trackListRoutingActivity` (как настройки слоёв: свой ключ, старый только читается). «Off» удаляет свой ключ.

### Связь со стором и картой

`web/src/routing/editing.ts` — `createRouteEditing({ store, router, notify })`, без React, как `createTrackActions`. В сторе:

- `routingActivity`, `routerReachable`;
- `routeEdit: { trackId, segment, line, drawing: 'start' | 'end' | null, canUndo, canRedo, preview } | null` — то, что рисует карта; `preview` — резинка от крайней точки к курсору при рисовании и положение перетаскиваемой точки.

На каждое изменение линии связь пишет треку `segments[segment]` и `routes[segment]` (длина в списке меняется сразу) и запоминает записанный массив отрезка. Редактор живёт и после выхода из редактирования — дожидается ответов и хранит историю (требование «История переживает выход»). При новом входе он берётся снова, только если отрезок в сторе — тот самый записанный массив: любое внешнее изменение (разворот, удаление трека) даёт другой массив, и редактор выбрасывается с отменой запросов, ответ которого иначе затёр бы чужую правку. Ответ, пришедший после выхода, пишет трек и обновляет запомненный массив, поэтому внешним изменением не считается. Трек скрыли, удалили или изменили снаружи во время редактирования — редактирование заканчивается.

Уведомления — в связи, а не в модели: `Routing failed: <причина>` на каждую ошибку маршрута; недоступный роутер — красная кнопка и одно предупреждение на переход «работал → упал» (`BRouter engine failed to load, reload the page to retry` / `BRouter is not running, start it with yarn local` + `. Lines stay straight until then.`), успешный маршрут снимает красноту.

### Отрисовка — GeoJSON-источники в стиле, как треки

`buildStyle(layers, tracks, edit)` добавляет над треками источники редактора (есть всегда, пустые без редактирования — порядок слоёв стабилен, как у треков):

- источник треков `tracks` — по фиче на отрезок (`id`, `segment`, `color`), редактируемый отрезок в него не попадает; поверх — `tracks-unrouted`: непроложенные отрезки всех треков пунктиром **[владелец]** (красный `#e11d48`, ширина 3) — пометка видна и вне редактирования;
- `route-edit-legs` — отрезки редактируемой линии, кроме ожидающих (разрыв): тонкая линия цвета трека (ширина 2.5, непрозрачная, как `weight 1.5, opacity 1` старого редактора), непроложенные — тем же пунктиром; `route-edit-hit` — тот же источник прозрачной линией шириной 14 для нажатия «вставить точку»;
- `route-edit-preview` — резинка и соседние отрезки перетаскиваемой точки, тонкий пунктир;
- `route-edit-waypoints` — опорные точки кружками (белые с тёмной обводкой, начало — зелёное, конец — красное, как классы старого редактора).

Спиннеры ожидающих отрезков — `<Marker>` react-maplibre с иконкой `LoaderCircle` и `animate-spin` в середине отрезка: их единицы, а анимация CSS проще символьного слоя. Данные треков в стиле пересобираются только при смене треков или редактируемого отрезка (`useMemo`). Превью перетаскивания и резинка — источник `route-edit-preview`, в стиле всегда пустой: данные ему ставит `MapEditor` через `setData` мимо стиля, потому что diff MapLibre обходит данные всех источников (замер — «Проверки»).

### События карты **[владелец]**

Компонент внутри `<Map>` (`useMap`) вешает обработчики MapLibre и `document`:

- клик: сначала опорная точка (`queryRenderedFeatures` по слою точек) — крайняя начинает рисование от своего конца, последняя поставленная заканчивает его; затем при рисовании — точка на карте (Alt — прямой отрезок); без рисования клик мимо линии заканчивает редактирование, по линии трека — начинает его;
- `mousedown`/`touchstart` по опорной точке — перетаскивание (`preventDefault` выключает панораму карты), по линии `route-edit-hit` — вставка точки и её перетаскивание; движение и отпускание — слушатели `window`, координаты — `map.unproject`; клик после такого нажатия гасится;
- `dblclick` по опорной точке — удаление, `preventDefault` гасит зум;
- клавиши на `keydown` у `document` (подвох macOS из `AGENTS.md`: пока зажат Cmd, `keyup` других клавиш не приходит): Cmd/Ctrl+Z, Cmd/Ctrl+Shift+Z, Ctrl+Y (по `event.code`, от раскладки не зависит), Backspace/Delete — убрать последнюю точку при рисовании, Escape/Enter — закончить рисование, без рисования Escape — редактирование; в полях ввода и редактируемом тексте — ничего;
- курсор карты: при рисовании — `crosshair`, пока есть ожидающие отрезки — `progress`, над опорной точкой — `move`.

Касание: точка ставится тапом (MapLibre шлёт `click`), опорная точка тянется пальцем; двойной тап остаётся зумом карты, удаление точки на телефоне — undo или будущее меню точки (`add-web-line-tools`).

### Интерфейс **[владелец]**

- Кнопка прокладки — в строке ввода списка треков, после «New track» (иконка `Route`): активна при выбранной активности, красная при недоступном роутере, со спиннером, пока движок загружается; подсказка — тексты спеки. Меню (shadcn `DropdownMenu`, радио-пункты): заголовок «Routing», «Off: straight lines», шесть активностей, внизу — подсказка, что делать, если роутер недоступен. Открытие меню перепроверяет живость.
- Панель редактирования — карточка снизу по центру карты, пока линия редактируется: цвет и название трека, подсказка («Click map to add points» при рисовании, «Click line end to continue» без него), кнопки Undo, Redo (недоступны, когда нечего), Done. Снизу посередине она не спорит со списком слева, слоями справа сверху и атрибуцией справа снизу; на телефоне 390 px помещается.
- «New track» — трек и сразу рисование (`addTrackAndEdit` старого клиента); «Add segment» в меню трека — новый отрезок с рисованием. Трек, оставшийся пустым после редактирования, удаляется; отрезок меньше двух точек — тоже.

### Выяснилось при apply

- Пустой маршрут — ошибка `no route found` и у движка, и у сервера (у старого серверного пути было `empty route`): спека browser-routing-engine требует этот текст, а двум текстам для одного случая причины нет **[агент]**.
- «Off» при сохранённом выборе старого клиента пишет в свой ключ пустую строку, а не удаляет его: иначе после перезагрузки снова подхватился бы `trackListRoutingActivity`, и «Off» не переживал бы перезагрузку **[агент]**.
- Связь со стором держит редакторы в `WeakMap` по массиву точек отрезка, который редактор записал последним, а не по номеру отрезка: номера сдвигаются при удалении отрезка, а ссылка на массив — это и ключ, и проверка «линию не меняли снаружи».
- Пункт `RadioItem` меню Base UI по умолчанию меню не закрывает (`closeOnClick` = `false`, `MenuRadioItem.d.ts`): выбор активности закрывает его явно, как контекстное меню старого клиента.
- Ломаная из ссылки или файла упрощается при импорте (`normalizeLine`), поэтому опорная точка, лежащая на прямой между соседями, пропадает; тесты берут линии с изломом.
- Синтетические события мыши в browser-тестах получают целые `clientX`/`clientY`: координата точки отличается от заданной на долю пикселя, сравнение — с допуском.
- **Перехват `importScripts` воркера в e2e ненадёжен.** `context.route` Playwright 1.64 видит запрос загрузчика CheerpJ из воркера движка не всегда: воркер успевает сходить в сеть до подключения перехвата, и тогда грузится настоящий рантайм с CDN (`cj3.wasm`, `11/lib/modules`, проверено 2026-10-09), а он через прокси `vite preview` стучится в `/tiles` (`ECONNREFUSED` в логе). Поэтому `e2e/fixtures.ts` подменяет сам скрипт воркера (`/next/assets/engine.worker-*.js` запрашивает страница — его перехват надёжен): перед кодом воркера встаёт `importScripts`, который вместо загрузчика выполняет заглушку. Адрес CDN тоже отвечает заглушкой — для запасного пути на главном потоке; запросы к CDN, которые увидел браузер, валят тест.
- **Фикстура `network` в e2e была ленивой.** Playwright создаёт фикстуру, только если тест её просит: тесты вида `async ({ page }) =>` (в том числе «Точка в адресе» и «Неизвестный ключ» из add-web-tracks) шли без перехвата — в настоящую сеть. Теперь фикстура `auto: true`.
- **Ревью диффа (субагент, 2026-10-09) и исправления.** Копия и разворот трека во время запроса оставляли в разметке `pending` без живого запроса — вечный разрыв со спиннером: теперь `settledRoute` делает такой отрезок непроложенным. Попадание по опорной точке и отрезку для кликов и нажатий считается по линии из стора через `map.project`, а не по отрисованному кадру: быстрый второй клик по только что поставленной точке ставил дубль. После тапа браузер шлёт совместимые `mousedown`/`click` — `mousedown` в течение 800 мс после касания игнорируется, иначе тап по линии вставлял две точки. Клавиши редактора не действуют во время перетаскивания, а при отпускании проверяется, что точка под этим номером та же. Enter обрабатывается только на карте или без фокуса (на кнопке в фокусе это её нажатие), клавиши в меню и окнах не трогаются. Новая точка встаёт на ближайшее звено, а не в точку нажатия в нескольких пикселях от линии.
- Редактируемая строка списка подсвечена (класс `edit` строки старого клиента) **[агент]**.

## Проверки

### Перетаскивание рядом с большим треком

2026-10-09, Vitest browser mode (Chromium 156 headless), временный тест вне репозитория: импорт GPX со случайным блужданием шагом до 0.0001°, затем новый трек из трёх точек, 60 движений перетаскивания средней точки, на каждое — ожидание следующего кадра (`requestAnimationFrame`), long tasks — `PerformanceObserver`.

| трек рядом | медиана кадра | p90 | long tasks за перетаскивание |
|---|---|---|---|
| нет | 16.7 мс | 17.2 мс | 1 (83 мс, начало перетаскивания) |
| 10 тыс. точек | 16.7 мс | 16.9 мс | 1 (71 мс) |
| 100 тыс. точек | 16.7 мс | 17.8 мс | 1 (78 мс) |

Кадр упирается в частоту экрана при любом размере трека рядом: diff стиля по данным треков в бюджет кадра укладывается. Одна долгая задача в начале перетаскивания не зависит от размера трека — первая отрисовка превью.

### Перетаскивание внутри большой редактируемой линии

Ревью нашло случай, которого первый замер не покрывал: редактируется сама импортированная линия, где каждая точка — опорная. Тот же стенд, линия из GPX с N точками (после упрощения импорта опорных меньше), перетаскивание её средней точки:

| точек в GPX (опорных) | превью через стиль: медиана / p90 | превью через `setData`: медиана / p90 | отпускание (запись трека) |
|---|---|---|---|
| 1 000 (≈ 750) | 16.7 / 18.0 мс | 16.7 / 17.2 мс | 34 мс |
| 10 000 (≈ 7 600) | 27.5 / 35.1 мс | 18.0 / 22.4 мс | 112 мс |
| 100 000 (≈ 76 000) | 107 / 144 мс | 177 / 201 мс | ≈ 1.6 с |

Поэтому превью (резинка, перетаскиваемая точка с прямыми до соседей) идёт через `setData` своего источника мимо стиля, а стиль меняется только в начале и в конце перетаскивания (`routeDrag`). На 76 тыс. опорных кадр упирается уже в отрисовку самих кружков и линии (разброс прогонов большой) — у старого клиента там были 76 тыс. DOM-маркеров. Что делать с такими линиями — backlog, «Редактор и активности».

## Risks / Trade-offs

- [Тысячи опорных точек у импортированной линии без разметки: каждая — кружок] → до ≈ 10 тыс. перетаскивание держит кадр; дальше — backlog «Редактор и активности».
- [Diff стиля обходит данные всех источников] → превью перетаскивания и резинка — `setData` мимо стиля; замеры — «Проверки»; на слабом телефоне не мерили.
- [Тост справа снизу на узком окне перекрывает правый край панели редактирования, пока не исчезнет] → тосты короткие; расположение — в `polish-web-ui`.
- [Разметка — номера точек: любой код, меняющий отрезок мимо стора, оставит неверные номера] → стор сбрасывает разметку при новых `segments` без `routes`; change 6 обязан не упрощать опорные точки.
- [e2e подменяет загрузчик CheerpJ: изменение API CheerpJ e2e не поймает] → настоящий движок проверяют стенд и синтетика прода (`clone-monitoring`).
