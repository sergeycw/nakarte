# clone-deploy Specification

## Purpose
Автоматическая публикация клона nakarte на Cloudflare из ветки `master` форка, чтобы прод всегда совпадал с `master` и не выкатывался без файлов движка.

## Requirements

### Requirement: Деплой на каждый push в master

Каждый push в `master` репозитория `sergeycw/nakarte` SHALL выкатывать сервисы, чьи файлы изменились с коммита последнего успешного прогона деплоя: сайт с Pages Functions — в Pages-проект `nakarte-routing`, Worker'ы — из своих каталогов `workers/<сервис>/`. Ручной запуск, изменение самого workflow деплоя или неизвестная база сравнения SHALL выкатывать всё. В других репозиториях деплой SHALL пропускаться.

#### Scenario: Слияние PR в master

- **WHEN** PR с изменениями приложения влит в `master` форка
- **THEN** через один прогон workflow «deploy pages» на `https://nakarte-routing.pages.dev` работает новая сборка

#### Scenario: Правка только документации

- **WHEN** в `master` пришёл push, который меняет только документы (`docs/`, `openspec/`, `*.md`) или другие workflow
- **THEN** ни Pages, ни Worker'ы не выкатываются, изоляты Worker'ов не перезапускаются

#### Scenario: Правка одного Worker'а

- **WHEN** push меняет только `workers/tracks/`
- **THEN** выкатывается только `nakarte-tracks`

#### Scenario: Push в апстрим или чужой форк

- **WHEN** workflow срабатывает не в `sergeycw/nakarte`
- **THEN** задание пропускается без обращения к Cloudflare

### Requirement: Сборка без файлов движка не выкатывается

Деплой SHALL собирать файлы движка (jar BRouter, обёртку, патч и профили) из образа `ghcr.io/abrensch/brouter:nightly` и SHALL падать до публикации, если в сборке нет `brouter-wasm/lib/brouter.jar` или `brouter-wasm/profiles/lookups.dat`.

#### Scenario: Файлы движка не собрались

- **WHEN** jar не попал в `build/brouter-wasm/lib/`
- **THEN** workflow падает до шага публикации, прод не меняется

### Requirement: Последний push побеждает

Если во время деплоя пришёл новый push, незаконченный деплой SHALL отменяться, и публиковаться SHALL последняя версия `master`. Изменения отменённого или упавшего прогона SHALL выкатываться следующим прогоном.

#### Scenario: Два push подряд

- **WHEN** второй push пришёл, пока первый деплой ещё идёт
- **THEN** первый прогон отменён, в проде сборка второго

#### Scenario: Отменённый прогон менял Worker

- **WHEN** прогон с изменением `workers/elevation/` отменён следующим push, который меняет только документацию
- **THEN** следующий прогон выкатывает `nakarte-elevation`

### Requirement: Бандл без адресов автора

Деплой SHALL после сборки проверять бандл скриптом `scripts/check-no-author-hosts.mjs` и SHALL падать до публикации, если в текстовых файлах сборки есть буквальный адрес `nakarte.me` или его поддомена. Та же проверка SHALL идти на каждом PR, который меняет приложение.

#### Scenario: Адрес автора в бандле

- **WHEN** в собранном бандле есть `https://proxy.nakarte.me/`
- **THEN** скрипт печатает вхождение с контекстом, workflow падает до шага публикации, прод не меняется

#### Scenario: Адрес автора в PR

- **WHEN** PR добавляет в приложение адрес `*.nakarte.me`
- **THEN** проверка `check web` на PR красная до merge

#### Scenario: Чистый бандл

- **WHEN** в бандле `nakarte.me` встречается только в экранированных регулярных выражениях разбора ссылок (`nakarte\.me`)
- **THEN** проверка проходит, деплой продолжается

### Requirement: Тесты сервиса перед его деплоем

Деплой каждого Worker'а SHALL идти после тестов этого сервиса на том же коммите, а публикация Pages — после тестов Pages Functions. Упавшие тесты SHALL останавливать деплой этого сервиса.

#### Scenario: Тест Worker'а упал

- **WHEN** в `master` попал коммит, на котором тесты `workers/tracks` красные
- **THEN** `nakarte-tracks` не выкатывается, прод остаётся на прежней версии

### Requirement: Worker'ы раньше Pages

Если в одном прогоне выкатываются Worker'ы и Pages, Pages SHALL публиковаться после успешного деплоя Worker'ов. Упавший деплой Worker'а SHALL останавливать публикацию Pages.

#### Scenario: Смена контракта сервиса и клиента одним PR

- **WHEN** PR меняет `workers/elevation/` и клиент
- **THEN** новый клиент появляется на `nakarte-routing.pages.dev` только после того, как выкачен новый `nakarte-elevation`

### Requirement: Секреты только у шагов публикации

В workflow деплоя секреты Cloudflare SHALL передаваться только шагам, которые зовут `wrangler`, а `wrangler` SHALL запускаться точной версией. Установка зависимостей, тесты и сборка SHALL идти без секретов. Действия GitHub в своих workflow SHALL закрепляться полным SHA коммита.

#### Scenario: Пакет со скриптом установки

- **WHEN** зависимость приложения при `npm ci` читает окружение процесса
- **THEN** `CLOUDFLARE_API_TOKEN` в нём нет

#### Scenario: Перезаписанный тег действия

- **WHEN** автор действия перенёс тег `v2` на другой коммит
- **THEN** workflow исполняет коммит, закреплённый в файле

### Requirement: Только текущий деплой Pages

После публикации Pages деплой SHALL удалять все остальные деплои проекта `nakarte-routing`, чтобы старые функции без новых лимитов не отвечали по `https://<хеш>.nakarte-routing.pages.dev`. Текущий деплой (тот, что отвечает на `nakarte-routing.pages.dev`) SHALL оставаться; если его не удалось определить или он собран не из коммита этого прогона, ничего не удаляется. Сбой удаления SHALL NOT помечать публикацию упавшей.

#### Scenario: Деплой после нескольких предыдущих

- **WHEN** Pages опубликованы, а у проекта есть старые деплои
- **THEN** после прогона у проекта один деплой, `https://<хеш старого>.nakarte-routing.pages.dev` не отдаёт функции

#### Scenario: Pages без Worker'ов

- **WHEN** в прогоне выкатываются только Pages, а деплой каждого Worker'а пропущен, потому что его файлы не менялись
- **THEN** старые деплои удаляются так же, как в прогоне, где выкатывались и Worker'ы

#### Scenario: Текущий деплой не определён

- **WHEN** Pages API не вернул текущий деплой проекта
- **THEN** деплои не удаляются, прогон сообщает об этом

### Requirement: Приложение в корне деплоя Pages

Публикация Pages SHALL содержать приложение из `web/` в корне сайта вместе с файлами движка. Перед публикацией деплой SHALL прогонять тесты приложения, e2e по той сборке, что будет опубликована, и проверку бандла на адреса автора; упавшие тесты или проверка SHALL останавливать публикацию Pages. Изменение только в `web/` SHALL выкатывать Pages.

#### Scenario: Правка только приложения

- **WHEN** push в `master` меняет только файлы в `web/`
- **THEN** Pages собираются и публикуются, Worker'ы не выкатываются

#### Scenario: Тест приложения упал

- **WHEN** в `master` попал коммит, на котором тесты `web/` красные
- **THEN** Pages не публикуются, на `/` остаётся прежняя версия

### Requirement: Ключ Google только шагу сборки

Деплой SHALL передавать значение секрета `GOOGLE_MAPS_API_KEY` в сборку приложения переменной `VITE_GOOGLE_MAPS_API_KEY` и только шагу этой сборки: установка зависимостей и тесты идут без него. Без секрета сборка SHALL проходить с пустым ключом, и Maps JavaScript API работает в режиме без ключа.

#### Scenario: Секрет не заведён

- **WHEN** секрета `GOOGLE_MAPS_API_KEY` нет
- **THEN** приложение собирается и выкатывается, Maps JavaScript API в нём загружается с пустым ключом

#### Scenario: Секрет заведён

- **WHEN** владелец завёл `GOOGLE_MAPS_API_KEY`
- **THEN** приложение загружает Maps JavaScript API с этим ключом, а e2e перед публикацией проходят на этой сборке
