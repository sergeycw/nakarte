## Коротко

- Границы сервисов в целом верные: высоты (API и тайлы) — один сервис на одних данных, треки отдельно, тайлы BRouter — Pages Function, потому что CheerpJ читает только свой origin. Слабое место — прокси: в одном Worker'е открытый прокси для импорта, прокси тайловых слоёв и Strava heatmap с секретом.
- Контракты сервисов повторяют клиент автора и меняются вместе с новым UI. Неизменны только ключи и данные в R2 (`tracks/{key}`, `nktk`, `NKE1`, `NKT1`, `*.rd5`), параметры адреса (`nktl=`, `nktk=`, коды слоёв `l=`) и адрес `nakarte-routing.pages.dev`, на который ведут старые ссылки.
- Данные перезаписываются на месте: `*.rd5` раз в неделю, архив тайлов высот — после пересборки. Версии в ключах нет, а клиент и изолят кешируют куски. Это главный риск данных. (Склейку в кеше браузера закрыл `fix-tile-cache-after-sync`; версии в ключах — нет.)
- Деплой не ждёт проверок и выкатывает всё на любой push: Worker'ы уходят без своих тестов, Pages — раньше Worker'ов. `workers/tiles` и `functions/brouter-wasm` без тестов вообще. (Исправлено 2026-10-08: `deploy-per-service`, `add-tiles-tests`.)
- Наблюдаемость почти нулевая: Workers Logs выключены, ошибок клиента не видно (а маршрут считается в браузере), проверки прода, кроме Strava, нет. (Workers Logs и проверка прода добавлены 2026-10-08 в `add-prod-monitoring`; ошибок клиента по-прежнему не видно.)
- Стоимость сейчас ≈ $5.25 в месяц (Workers Paid + ≈ 17 ГБ R2 сверх бесплатных 10 ГБ) и растёт медленно: ≈ $26 на каждый миллион маршрутов сверх ≈ 250 тыс. в месяц. Дорогой путь — API высот на точках вразброс (до тысяч чтений R2 на вызов).
- Переезд с Cloudflare — около недели работы и VPS: ядро высот уже переносимо, треки и прокси — небольшой JS, тайлы BRouter — любая статика с Range. Платформенные вещи — привязка rate limiting, Pages Functions, кеш изолята.

## 1. Границы сервисов

**Как сейчас.** Четыре точки входа на Cloudflare (блоки ③–⑥, [уровень 2](../../docs/architecture/README.md#публичный-клон)):

| Сервис | Где код | Как деплоится | Данные |
|---|---|---|---|
| Тайлы BRouter | [workers/tiles/src/index.js](../../workers/tiles/src/index.js) через [functions/tiles](../../functions/tiles/[[path]].js) | с Pages | R2 `nakarte-tiles` |
| Файлы движка (jar, профили) | [functions/brouter-wasm](../../functions/brouter-wasm/[[path]].js) | с Pages | статика `build/` |
| CORS-прокси | [workers/cors-proxy](../../workers/cors-proxy/src/index.js), [strava.js](../../workers/cors-proxy/src/strava.js) | отдельный Worker | секреты Strava |
| Треки | [workers/tracks](../../workers/tracks/src/index.js) | отдельный Worker | R2 `nakarte-tracks` |
| Высоты, API и тайлы | [workers/elevation](../../workers/elevation/core/src/http.rs) | отдельный Worker | R2 `nakarte-elevation` |

**Что мешает.**

- Прокси совмещает три роли с разным риском: импорт по любой ссылке (`simpleService` в [services](https://github.com/sergeycw/nakarte/blob/015be893/src/lib/leaflet.control.track-list/lib/services/simpleService.js) отдаёт прокси произвольный URL), тайловые слои с конечным списком хостов ([layers.js](https://github.com/sergeycw/nakarte/blob/015be893/src/layers.js), `urlViaCorsProxy`) и Strava heatmap с секретом сессии. Лимит частоты один на всё (1200 в минуту, [wrangler.toml](../../workers/cors-proxy/wrangler.toml)), поднят ради тайлов, и импорт получил его же. Список целевых хостов не ограничен: прокси открыт для любого адреса, если подделать `Origin`.
- Тайлы BRouter и файлы движка — одна функция по смыслу («файлы движка по Range с того же origin»), но два кода: `functions/tiles` берёт Range у R2, `functions/brouter-wasm` разбирает Range сам и на каждый запрос читает ассет целиком (`asset.arrayBuffer()`, `brouter.jar` — 2.3 МБ). При этом `workers/tiles` выглядит как сервис (свой `wrangler.toml`), но деплоем им не является.
- Профили и `lookups.dat` движка приезжают из образа `brouter:nightly` в сборку Pages, а тайлы — из brouter.de в R2: одна версия данных BRouter живёт в двух хранилищах с разным циклом обновления (риск уже в backlog, «Внешние зависимости и риски», пункт brouter.de).

**Варианты.**

1. Оставить как есть.
2. Прокси: список разрешённых хостов для тайловых слоёв и Strava, отдельный счётчик частоты на импорт по ссылке; Strava heatmap — отдельным маршрутом или Worker'ом со своим лимитом.
3. Файлы движка: jar и профили положить в R2 рядом с тайлами под версией BRouter (см. [п. 3](#3-хранилища-и-форматы-данных)) и отдавать одной функцией через Range R2. `functions/brouter-wasm` и чтение ассета целиком уходят.
4. Слить треки и высоты в один Worker. Не рекомендую: разные данные, разные лимиты CPU (500 мс против 10 с), Rust и JS.

**Рекомендация.** Варианты 2 и 3. Слияния Worker'ов не нужно. Как именно ограничить прокси (список хостов, лимит на импорт) — решает [Security-аудит](#5-cors-и-граница-защиты), здесь только граница: прокси должен знать, кого он проксирует.

**Цена.** Вариант 2 — день, плюс сбор списка хостов из `layers.js` и сервисов импорта. Вариант 3 — день-два вместе с версионированием данных.

## 2. Контракты

**Как сейчас.** Сервисы повторяют протоколы автора, клиент почти не менялся (спеки [track-storage](../specs/track-storage/spec.md), [elevation-api](../specs/elevation-api/spec.md), [elevation-tiles](../changes/archive/2026-10-07-add-elevation-tiles/design.md), [cors-proxy](../specs/cors-proxy/spec.md)). Адреса Worker'ов — в [src/config.js](https://github.com/sergeycw/nakarte/blob/015be893/src/config.js), их можно менять без миграции данных.

| Контракт | Держится ради старого клиента | Можно поменять с новым UI | Менять нельзя |
|---|---|---|---|
| Треки: `POST`/`GET /track/{key}`, тело — строка `nktk` | `withCredentials: true` в клиенте ([track-list.js](https://github.com/sergeycw/nakarte/blob/015be893/src/lib/leaflet.control.track-list/track-list.js), [services/nakarte](https://github.com/sergeycw/nakarte/blob/015be893/src/lib/leaflet.control.track-list/lib/services/nakarte/index.js)) — отсюда отражённый `Origin` вместо `*`; ссылка копируется до ответа сервера | CORS без `credentials`; ответ о записи до копирования ссылки; адрес и путь (`/v2/…`) | ключ = base64url(md5(тело)) и объекты `tracks/{key}`: на них держатся выданные ссылки `nktl=`; разбор `nktk` всех версий (сейчас 1–4, [nktk.js](https://github.com/sergeycw/nakarte/blob/015be893/src/lib/leaflet.control.track-list/lib/parsers/nktk.js)) |
| Высоты: `POST /`, строки `lat lng` → строки `%.2f`/`NULL` | текстовый формат и тексты ошибок Go-сервера автора, контрактный тест на эталонах автора | JSON или бинарный формат, пакет точек трека одним запросом, без `credentials` | — (данных пользователей нет) |
| Тайлы высот: 256×256 `Int16` дельты, gzip, `-512` | формат декодера [elevation-display](https://github.com/sergeycw/nakarte/blob/015be893/src/lib/leaflet.layer.elevation-display/index.js) | любой формат, например Terrain-RGB под MapLibre | — |
| Прокси: `/{http,https}/{host}/{path}`, `/wikimapia/` | `urlViaCorsProxy` во всём клиенте; `HEAD` как `GET` ради коротких ссылок mapy.com | явные маршруты по ролям (`/tiles/<слой>/…`, `/import?url=`), без `HEAD`-трюка | — |
| Адрес приложения: `#m=`, `l=`, `nktk=`, `nktl=`, `nktu=`, `nktp=`, `nktj=` | — | новые параметры можно добавлять | разбор существующих параметров и старых кодов слоёв (требование «Старые коды удалённых слоёв» в [clone-hosting](../specs/clone-hosting/spec.md)); хост `nakarte-routing.pages.dev` или редирект с него |
| Маршрут: запрос BRouter (`lonlats`, `profile`, `profile:<переменная>`) | — | — | формат BRouter, это контракт движка, а не автора |

**Что мешает.** Ничего срочного: контракты работают и покрыты тестами. Но переписывать их по одному, без нового клиента, бессмысленно — выигрыш появляется только вместе с UI.

**Рекомендация.** До нового UI контракты не трогать. С новым UI ввести версию в путь (`/v2/`) у треков и высот, держать `v1` до отключения старого клиента; хранилище треков и разбор `nktk` оставить навсегда. Записать в [track-storage](../specs/track-storage/spec.md) отдельным требованием, что ключ и формат объекта неизменны (сейчас это следует из сценариев, но прямо не сказано).

**Цена.** Ноль до UI; с UI — по change на сервис, по 1–2 дня.

## 3. Хранилища и форматы данных

**Как сейчас** (Cloudflare GraphQL Analytics, максимум за 30 дней на 2026-10-08):

| Бакет | Объектов | Объём | Ключи и формат | Как обновляется |
|---|---|---|---|---|
| `nakarte-elevation` | 26 158 | 16.9 ГБ | `dem3/N43E042` — заголовок `NKE1` ([format.rs](../../workers/elevation/core/src/format.rs)); `tiles/elevation-z0-9` — заголовок `NKT1`, плотный индекс ([archive.rs](https://github.com/sergeycw/nakarte/blob/68ab4954/workers/elevation/core/src/archive.rs)) | вручную, S3 API ([ci-cd.md](../../docs/architecture/ci-cd.md)) |
| `nakarte-tiles` | 1 143 | 10.0 ГБ | `<имя>.rd5` как у brouter.de, `manifest.json` (`lookupsSha256`, версия тайла = дата и размер из индекса brouter.de) | по понедельникам, `wrangler r2 object put` поверх старого ([brouter-tiles-sync.mjs](../../scripts/brouter-tiles-sync.mjs)) |
| `nakarte-tracks` | 3 | 172 байта | `tracks/{key}`, тело — `nktk` (версия — первый байт строки) | запись из Worker'а, без метаданных |

Версии форматов: у `dem3` и архива есть magic с номером (`NKE1`, `NKT1`), у `nktk` — номер версии внутри строки. У `*.rd5` и файлов движка версии нет, есть только `lookupsSha256` в манифесте.

**Что мешает.**

- Перезапись на месте. Тайл `*.rd5` заменяется под тем же ключом, а `functions/tiles` отдаёт его с `Cache-Control: public, max-age=86400` ([workers/tiles/src/index.js](../../workers/tiles/src/index.js)). Движок читает тайл кусками по Range: если между чтениями объект сменился или часть кусков пришла из кеша браузера, а часть — новая, BRouter получит индекс от одной версии и данные от другой. Проверено 2026-10-08 на `wrangler dev`: после перезаписи объекта Chrome на `bytes=0-29` склеил 10 старых байт из кеша и 20 новых из сети. Кеш браузера закрыт `no-store` (`fix-tile-cache-after-sync`); остаётся страница, открытая во время синхронизации (часы, ≈ 10 ГБ): движок держит индекс старой версии тайла.
- Архив тайлов высот — один объект; после перезаливки нужен передеплой Worker'а, потому что кеш изолята держит страницы старого индекса (подвох записан в `AGENTS.md`, «Сервис высот»). Это ручной шаг, который легко забыть.
- Синхронизация `*.rd5` использует `wrangler`, а данные высот — S3 API. Два инструмента для одного R2; `wrangler` медленнее и привязан к Cloudflare.
- `functions/tiles` отдаёт любой ключ бакета, в том числе `/tiles/manifest.json`. Утечки нет (в манифесте только версии), но служебный файл лежит в публичном пространстве.
- Треки без метаданных: ни времени записи, ни версии `nktk` в метаданных объекта. Для чистки или миграции придётся читать каждое тело.

**Варианты.**

1. Версия в ключе: `rd5/<снимок>/<имя>.rd5` и `engine/<digest образа>/…`, манифест указывает текущий снимок, клиент берёт путь из манифеста или из сборки. Старый снимок удаляется через неделю. Хранение на время перехода удваивается (≈ +10 ГБ, ≈ $0.15 в месяц).
2. Content-addressed ключи (хеш тела). Надёжнее, но нужен индекс имя → хеш на клиенте.
3. Оставить и сократить `max-age` до часа. Сужает окно, но не закрывает его.

Для архива высот — то же: `tiles/elevation-z0-9-<версия>`, версия в `[vars]` Worker'а, смена версии = деплой, который и так нужен.

**Рекомендация.** Сначала проверить гипотезу о смешанных версиях (запрос тайла до и после `put`, `ETag` и поведение кеша браузера). Если подтвердится — вариант 1 вместе с [переносом файлов движка в R2](#1-границы-сервисов). Синхронизацию перевести на S3 API (как высоты). В `functions/tiles` раздавать только `*.rd5` и пустой `storageconfig.txt`. Треки писать с `customMetadata` (время, версия `nktk`).

**Цена.** Проверка — час; версионирование — 1–2 дня; S3 API в синхронизации — полдня; метаданные треков — час.

## 4. Шаблон сервиса: тесты, CI, деплой

**Как сейчас.** Правила — `AGENTS.md`, [«Свои бэкенды вместо `*.nakarte.me`»](../../AGENTS.md#свои-бэкенды-вместо-nakarteme), схема — [ci-cd.md](../../docs/architecture/ci-cd.md). У `cors-proxy`, `tracks`, `elevation` свой workflow `check-<сервис>.yml` с `paths:`, тесты в `workerd` без сети. Деплой — один job [deploy-pages.yml](../../.github/workflows/deploy-pages.yml) на каждый push в `master`: Pages, потом три Worker'а. Прогон ≈ 2 минуты (Rust из кеша `rust-cache`).

**Что мешает.**

- Деплой не ждёт проверок. `deploy pages`, `check` и `check-<сервис>` стартуют на одном push параллельно, `master` не защищён (`gh api …/branches/master/protection` → `Branch not protected`). Worker с упавшими тестами выкатится.
- Пункт backlog «`deploy pages` … выкатывает все три Worker'а» подтверждён, но цена — не время сборки (2 минуты), а побочные эффекты: каждый деплой Worker'а — новые изоляты, то есть холодный кеш высот (до 32 МБ) и новое обновление кук Strava на изолят. Правка документации сбрасывает кеши прода.
- Порядок: Pages раньше Worker'ов. Если change меняет контракт сервиса и клиент одним PR (так велит монорепо), новый клиент несколько минут ходит в старый Worker.
- `workers/tiles` и `functions/brouter-wasm` без тестов и без workflow, хотя `AGENTS.md` требует тесты у каждого сервиса. Range-логику CheerpJ проверяют только руками.
- `check-no-author-hosts.mjs` запускается только в деплое: PR с адресом автора пройдёт проверки и упадёт уже после merge.
- `main.yml` — апстримный файл на `actions/*@v2`, его не трогаем по правилу; матрица karma включает Firefox 52 ESR. Это касается [UI](#что-влияет-на-переписывание-ui).

**Варианты.**

1. Job на сервис в `deploy-pages.yml` с фильтром путей (`dorny/paths-filter` или `git diff` в шаге) и `needs:` на тесты этого сервиса; Worker'ы до Pages.
2. Деплой через `workflow_run` после зелёного `check`. Сложнее: несколько workflow проверок, а `workflow_run` смотрит на один.
3. Защита `master` с обязательными проверками. Настройка репозитория, решает владелец; при merge самим агентом это то же требование «зелёные checks перед merge», которое сейчас держится на дисциплине.

**Рекомендация.** Вариант 1: тесты сервиса — шаг того же job перед деплоем (не нужно ждать чужой workflow), Worker'ы перед Pages, проверка бандла — ещё и в PR (`check` трогать нельзя, значит в отдельном `check-clone.yml` вместе со сборкой клона). Тесты для `functions/` по шаблону `workers/tracks`: `vitest` с локальным R2 и ассетами. Вариант 3 — вопрос к владельцу.

**Цена.** День на деплой по сервисам, полдня на тесты функций, полчаса на защиту ветки.

## 5. CORS и граница защиты

Только архитектура; атаки и расходы — пункт backlog «Security-аудит клона», здесь не повторяются.

**Как сейчас** ([protection.md](../../docs/architecture/protection.md)). Граница проходит внутри каждого Worker'а: потолок CPU и подзапросов платформы → `Origin` из `ALLOWED_ORIGINS` → счётчик частоты по `CF-Connecting-IP` → лимиты обработчика. Перед Worker'ами ничего нет: своего домена нет, значит нет зоны и WAF, `*.workers.dev` открыт всем. Pages Functions без счётчика частоты. В аккаунте есть бюджетные оповещения: `nakarte early warning $3`, `nakarte near limit $8` и автоматическое (Cloudflare API, `alerting/v3/policies`).

**Что мешает.**

- `Origin` подделывается, поэтому реальная граница — счётчик частоты. А он, по [документации Cloudflare](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), локален для каждой локации и приблизителен: распределённый клиент его обходит. Спека [worker-limits](../specs/worker-limits/spec.md) это признаёт.
- Нет потолка расходов сверху: бюджетные оповещения только пишут письмо, а не останавливают Worker'ы.
- Ограничение «кого можно проксировать» отсутствует (см. [п. 1](#1-границы-сервисов)).
- `withCredentials` в клиенте заставляет отражать `Origin`; для защиты это ничего не даёт, но усложняет CORS и тесты.

**Рекомендация.** Принять как модель: «CORS защищает пользователей, бюджет защищают частота, потолки на вызов и оповещения». Свой домен — единственный путь к WAF и rate limiting на уровне зоны; он же нужен для Cache API и переименования ([п. 8](#8-переносимость-с-cloudflare)). Что именно и где ставить — передаю в Security-аудит.

## 6. Наблюдаемость

**Что видно сейчас.**

| Что | Где | Ограничение |
|---|---|---|
| Живой поток логов | `npx wrangler@4 tail` из каталога Worker'а | только пока запущен; истории нет |
| Источник кук Strava | заголовок `X-Strava-Cookies`, workflow `strava heatmap check` раз в день, письмо GitHub при падении | один сценарий из всех |
| Падения синхронизации и заливок | письмо GitHub о красном workflow | расписание отключается после 60 дней без коммитов |
| Запросы, CPU, ошибки, операции R2 | Cloudflare GraphQL Analytics и дашборд | никто не смотрит регулярно |
| Расходы | бюджетные оповещения $3 и $8 | только деньги, не поломки |

У всех трёх Worker'ов `observability: null` и `logpush: false` (Cloudflare API, `script-settings`), в `wrangler.toml` блока `[observability]` нет — Workers Logs выключены. В клиенте `sentryDSN` и `eventsLogUrl` пустые ([config.js](https://github.com/sergeycw/nakarte/blob/015be893/src/config.js)).

**Чего не хватает.**

- Ошибок клиента. Маршрут в клоне считает браузер; отказ CDN CheerpJ, исключение Java, пустой трек или `Routing failed` видит только пользователь.
- Проверки прода после деплоя: открывается ли сайт, отвечают ли `/tiles/*.rd5` с `206`, API высот на эталонной точке, тайл высот, `GET` известного трека.
- Истории логов Worker'ов: причину `500` вчера сейчас не найти.
- Свежести данных: дата последней успешной синхронизации тайлов нигде не видна, кроме `manifest.json`.

**Варианты.** Workers Logs (`[observability] enabled = true`, `head_sampling_rate` меньше 1 для прокси с тайлами): по [прайсу Workers](https://developers.cloudflare.com/workers/platform/pricing/) 20 млн событий в месяц включены в Paid, дальше $0.60 за миллион, хранение 7 дней; с 2026-12-01 цены переходят на Cloudflare Observability. Ошибки клиента — Sentry (бесплатный план, DSN уже поддержан кодом) или свой `POST /events` в существующий Worker с записью в Workers Logs. Синтетика — workflow по образцу `strava heatmap check`, после деплоя и раз в день.

**Рекомендация.** Синтетика и Workers Logs — до переписывания UI: они дадут базовую линию, с которой сравнивать новый клиент. Ошибки клиента — вопрос владельцу (сторонний Sentry или своё).

**Цена.** Синтетика — полдня; Workers Logs — час; ошибки клиента — день.

## 7. Стоимость

**Цены** (первоисточники, 2026-10-08):

- [Workers](https://developers.cloudflare.com/workers/platform/pricing/): Paid $5 в месяц, включены 10 млн запросов и 30 млн CPU-мс, дальше $0.30 за миллион запросов и $0.02 за миллион CPU-мс. Pages Functions тарифицируются как Workers, запросы к статике бесплатны.
- [R2](https://developers.cloudflare.com/r2/pricing/): хранение $0.015 за ГБ-месяц, класс A $4.50 и класс B $0.36 за миллион; бесплатно 10 ГБ, 1 млн A, 10 млн B в месяц; egress бесплатный. `GetObject` и `HeadObject` — класс B, `PutObject` и `ListObjects` — класс A.
- Привязка rate limiting в прайсе не упомянута.

**Использование** за всё время жизни клона (2026-10-06 — 2026-10-08, Cloudflare GraphQL Analytics):

| Что | Запросов | CPU | Заметки |
|---|---|---|---|
| `nakarte-cors-proxy` | 15 619 | 15.7 с, p99 2.4 мс | 446 `clientDisconnected` — тайлы, брошенные при прокрутке |
| `nakarte-elevation` | 293 | 21.5 с, p50 2 мс, p99 2.96 с | тяжёлый хвост — API на тысячах точек |
| `nakarte-tracks` | 28 | 0.02 с | |
| Pages Functions | 1 704 | p99 4.6 мс | 813 подзапросов (R2 и ассеты) |
| R2, класс A | ≈ 28 тыс. | | почти всё — заливка `dem3` и тайлов |
| R2, класс B | ≈ 63 тыс. | | в основном генерация архива тайлов высот |

**Сейчас:** $5 Workers Paid + ≈ 17 ГБ сверх бесплатных 10 ГБ × $0.015 ≈ $0.25 = **≈ $5.25 в месяц**. Операции и запросы в бесплатных объёмах.

**Как растёт** (сверх включённого; цены выше):

| Единица | Что тратит | Стоимость |
|---|---|---|
| Маршрут в клоне | ≈ 40 Range-чтений `*.rd5` (оценка [sync-world-tiles](../changes/archive/2026-10-07-sync-world-tiles/design.md)) = 40 вызовов функции + 40 класса B | ≈ $26 на миллион маршрутов; бесплатно ≈ 250 тыс. в месяц, если другого трафика нет |
| Запуск движка | Range-чтения jar и профилей, каждое — вызов функции и чтение ассета целиком | число чтений на запуск не измерено |
| Тайл через прокси | 1 запрос, ≈ 1 мс CPU | ≈ $0.32 на миллион |
| Тайл высот | 1 запрос; z10–11 — до 4 чтений класса B на промах кеша | ≈ $0.30–1.75 на миллион |
| API высот, трек | 1 запрос, чтения кусков вдоль трека (не измерено) | доли цента на тысячу |
| API высот, 10 000 точек вразброс | до ≈ 3–4 с CPU и до тысяч чтений класса B | при ≈ 2 000 чтений ≈ $0.0008 за вызов, ≈ $800 на миллион — самый дорогой путь |
| Ссылка на треки | 1 класса A + хранение | $4.50 на миллион ссылок |
| Workers Logs, если включить | событие на запрос | $0.60 на миллион сверх 20 млн |
| Высоты GLO-30 | +70–110 ГБ (backlog, «Глобальное направление») | ≈ $1–1.7 в месяц |

Фиксированная часть — $5 + хранение, переменная до сотен тысяч маршрутов в месяц почти нулевая. Расходы ломает не рост пользователей, а злоупотребление API высот и прокси — это Security-аудит.

## 8. Переносимость с Cloudflare

**Что завязано на платформу.**

| Компонент | Привязка | Замена | Цена переезда |
|---|---|---|---|
| Статика клона | Pages | любой статический хостинг | часы |
| `functions/tiles`, `functions/brouter-wasm` | Pages Functions, привязка R2, `ASSETS` | nginx или Caddy с Range на том же origin; файлы на диске или S3 | полдня |
| `nakarte-tracks` | `env.TRACKS` (R2), привязка rate limiting | Node или Deno + S3 или диск; лимит — nginx `limit_req` | день |
| `nakarte-cors-proxy` | `fetch` Worker'а, `ctx.waitUntil`, кеш кук в изоляте, IP Cloudflare | Node-сервер, кеш в памяти процесса; другие IP — другие блокировки у сайтов | 1–2 дня |
| `nakarte-elevation` | `workers-rs` только в крейте `worker` (170 строк); ядро без ввода-вывода | адаптер `axum` уже есть ([server](../../workers/elevation/server/src/lib.rs)), данные на диск (≈ 17 ГБ) | день |
| Данные | R2: S3 API у высот, `wrangler` у тайлов BRouter | любое S3; синхронизация тайлов — переписать на S3 API | полдня |
| Защита | rate limiting по локациям, бесплатная защита от DDoS | своя; DDoS-защиту не заменить дёшево | — |

Итого около недели работы и VPS. Причина остаться — в [решении о Cloudflare](../changes/archive/2026-10-08-record-platform-decisions/design.md): egress бесплатный, нет администрирования, VPS не дешевле.

Из того, что дешево сделать заранее: синхронизацию тайлов через S3 API и версионированные ключи — они нужны и на Cloudflare. Pages Cloudflare развивает медленнее Workers: по [руководству миграции](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/) у Workers «distinctly broader set of features», а статика там тоже бесплатна. Переезд Pages → Worker со статикой даст один Worker на сайт, тайлы и файлы движка; поддерживает ли статика Worker'а Range с `206`, в документации не сказано — проверить до решения.

## Что влияет на переписывание UI

- **Контракты.** Новый UI может сменить форматы высот, тайлов высот, протокол прокси и CORS (см. [п. 2](#2-контракты)); обязан читать старые адреса (`nktl=`, `nktk=` всех версий, коды слоёв `l=`) и жить на `nakarte-routing.pages.dev` или редиректить с него.
- **Движок.** Один library-поток CheerpJ на страницу, очередь запросов, прогрев при выборе активности, 0.6–0.8 ГБ памяти — ограничения для любого UI ([browser-routing-engine](../specs/browser-routing-engine/spec.md)). Файлы движка и тайлы должны идти с origin страницы: хостинг нового UI обязан отдавать `/tiles/` и `/brouter-wasm/` с `206`. Ответ владельца про сервер роутинга ([вопросы](#оценка-сейчас-и-вопросы-владельцу)) может снять всё это.
- **Стек.** `leaflet` 1.0.3, `knockout` 3.4 и Firefox 52 ESR в CI — ответ про старые браузеры и векторные тайлы определяет выбор между Leaflet и MapLibre.
- **Поведение.** Спеки [routing](../specs/routing/spec.md) и [route-editing](../specs/route-editing/spec.md) — контракт для нового редактора; два требования без причины («прямой отрезок при ошибке», «ссылки только с геометрией») стоит решить до переноса, а не переносить молча.
- **Наблюдаемость.** Синтетика и ошибки клиента до переписывания дадут, с чем сравнить новый клиент.
- **Конфиг.** Склейка `config.js` + `secrets.js` + `config-target` ([client.md](../../docs/architecture/client.md#как-собираются-адреса-сервисов)) — единственное место различий сборок; новый UI должен сохранить один такой контракт.
